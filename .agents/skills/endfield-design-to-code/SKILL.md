# 人のデザイン原稿を実装へ反映する

外観の正本は[現在のFig](../../../art-src/openpencil/endfield-rpg.fig)、ゲームの振る舞いは[仕様概要](../../../specs/overview.md)と各仕様に従う。
原稿の編集・図案や素材の制作・審美判断は人が担当する。AIは原稿の構造を読み、実装・Story・対応設定・検証を担当する。
別途明示された依頼がない限り、AIはFigを編集・再生成・再構築せず、比較成功のために原稿を自動修復しない。
起動・CLI・素材出力は[README](../../../README.md#openpencilでデザインマスターを編集する)、検証の選択と提出条件は[テスト設計](../../../docs/testing.md#デザイン原稿と実装の比較)を正本とする。

## 1. 変更の意味と影響範囲を読む

1. 依頼、現在のFig、関連仕様、既存のSvelte部品・CSSトークン・公開props・Storyを照合する。
2. READMEの既存CLIと検証結果から、ページ、ノードのパス／GUID、部品・インスタンス、標準プロパティ、Variants、変数・スタイル、素材参照を調べる。
3. 有効な成功済みsignatureがあれば`npm run openpencil:verify -- --diff`で影響対象IDと選択理由を確認する。これは属性ごとの変更内容を示す機能ではない。
4. 変更内容が必要ならGit上の変更前と現在のFigから実際のノードデータを読み、追加・削除・改名、構造・制約・props・状態・参照の違いを確認する。新旧ファイルや既存の変更を上書きしない。
5. 変更した部品だけでなく、そのインスタンス・共有定義・画面への影響と、実装／Story／対応設定の更新先を特定する。

パス／GUIDによる対応は削除・改名・部品追加で壊れうる。旧対象を黙って落とさず、意図した変更を読んで対応の更新・追加・削除を決める。
意図や仕様との優先関係が実際に曖昧な場合、または依頼外のデザイン変更が必要な場合だけ人に確認する。独立して進められる実装・調査は続ける。

## 2. 製品部品とStoryを更新する

1. 既存のSvelte部品・props・トークン・製品素材で原稿を実装し、ゲームの状態・意味イベント・責務境界を保つ。
2. 部品と同居する`*.stories.ts`を更新する。各外観variantは実製品部品を独立して描画し、その状態を決める意味のある公開propsを各Storyの`args`へ明記する（DAMP）。
3. 基礎データを共有しても、そのケースの前提・差分・期待結果を隠さない。単体部品の入力を得るために画面全体やゲーム状態を生成するfactoryを作らない。
4. `parameters.design`に原稿ノード・variant・比較条件を反映する。標準indexとprepared parametersによる既存集計を使い、別の手書き対応表を増やさない。
5. hover・focus・pressed・選択・dialogなどは公開propsと通常のブラウザ入力／`play`で再現する。比較専用のUI・状態・CSSクラスを製品へ足さない。

共通hostはテーマ・使用可能な寸法・paddingだけを担う。親画面を描いて隠す、親の実測座標を転写する、部品をPNGへ平坦化する方法は使わない。
部品全体と外観が変わるvariant・必要状態、複数部品を配置する画面コンポーネントを比較する。
任意の文字列・数値・座標の列挙、内部の文字・アイコン・素材画像単体、操作手順だけのStoryを比較対象へ増やさない。
戦闘HUD等のUI部品は対象にできるが、開発エディター・戦闘FX・3D画面のFigフレームは作らない。
人が変更した図案の出力には既存の素材設定とexport処理を使い、AIが新しい図案や美的解釈へ置き換えない。

## 3. 固定環境で比較し、不一致の原因を分ける

1. 反復は有効な成功済みsignatureを使う`npm run openpencil:verify -- --changed`を優先する。初回・無効signature・提出前の実行範囲はテスト設計に従い、不要な全件再生成を前置しない。
2. 限定調査には既存の`--select`、構造の確認には`--list`、HTML・素材の調査には`--keep-export`を使う。部分実行や一覧取得を全体の合格と扱わない。
3. 既存の固定Docker内でOpenPencilの標準HTML出力と独立Storyを撮影する。CanvasKitの直接PNG出力を比較用参照へ代用しない。
4. 原稿と実装の撮影条件を揃え、寸法一致かつ全画素・全RGBAの差分0だけを成功とする。許容差・マスク・拡縮・色補正を加えず、生成PNGをbaselineとしてコミットしない。
5. `test-results/openpencil/verification/report.json`と参照／実装／差分PNGを読み、対象ID・ノード・変更内容に対応する原因を絞る。

不一致は実装、撮影環境、素材、フォント、DPR／寸法／拡縮、HTML exporterを分けて調べる。症状だけでデザインや実装の責任を決めない。
製品実装の誤りを直して再比較する。環境やexporterの不具合は根拠と再現条件を示し、実装の見た目を崩して補償しない。
原稿の不正な構造はページ・ノードのパス／GUIDと、影響する表示・操作・exportの具体的な問題を報告する。AIによるFig修復へ進まない。
通常の製品入力では到達できない状態や人のデザイン判断が必要な問題は、その対象と原因・未確認事項を示す。比較のために状態を捏造したり対象を黙って除外したりしない。

## 4. 必要な検証と結果を残す

変更に必要な型・部品操作・画面結合・ゲーム側の検証と提出前確認は[テスト設計](../../../docs/testing.md)に従う。コマンドの版・寸法・状態数・閾値をここへ複製しない。
更新した実装／Story／ノード対応、実行した範囲・結果、差分0を確認した対象、残る不一致・人の判断が必要な箇所を具体的に報告する。
既存の依頼内で進められる作業に新たな承認工程を足さず、Figの自動編集や未実行の比較を完了扱いにしない。
