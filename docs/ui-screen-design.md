# 画面設計

画面の目的から、必要な情報、操作、部品の組合せを決める方法を定める。表現の共通規則は[デザインシステム](design-guidelines.md)、制作・実装・検証は[制作手順](ui-asset-production.md)を参照する。ゲーム規則は[specs](../specs/overview.md)を正本とし、設計票へ複製しない。

## 情報と配置を組み立てる順序

1. プレイヤーの目標、到達経路、完了条件、対象外を決める。画面を開くこと、選ぶこと、実行することを分ける。
2. 情報0個から始め、目標に必要な判断ごとに情報と操作を追加する。現在ある要素も、残す理由を同じ基準で確認する。
3. 全パーツを棚卸しし、文字・数値・図案・ラベル・枠・面・状態表示を、それを含む完成部品へ対応付ける。
4. 判断を支える情報と操作を、用途、構造、状態、ラベル、入力、読取りやすさから検討する。共通規則で不足する場合は、本作の実画像で問題と改善の仮説を具体化する。必要に応じて参考資料も調べ、対象画面に成立するかを確かめる。
5. 共通DSに必要な契約を定め、全パーツへfamily／variant／token／stateを割り当てる。未確定の部品を残したまま画面案を完成扱いにしない。
6. 情報の関係、視線と入力の順序、優先度から構図を作る。固定版のFigmaと必要な状態画像で、局所と全体の見た目を確認する。

寸法や構成は、本作の実書体・図案・背景・表示条件で判断する。旧CSS、背景や立ち絵の既存配置を、新しい構図の自動的な制約にしない。対して、本人が指定した保持条件と承認済み固定版は変更範囲の制約として守る。

## 画面ごとに決めること

設計票は画面仕様へ置き、未決、表示案、実装済み、承認対象を取り違えない。必要な項目を対象に合わせて記す。既存の承認範囲へ位置を合わせる修正なら、その設計を参照し今回の差を特定する。

| 項目 | 記す内容 |
| --- | --- |
| 目的と範囲 | 何を判断・完了する画面か、入口・出口、今回変える対象、対象外 |
| 判断と情報 | 各情報が必要な理由、データの正本、常設／必要時／別画面、優先度 |
| 全パーツ割当 | 完成部品、family／variant／token／state、図案・文字・枠等の構成、選択理由 |
| 全操作 | 入力方式、操作名、許可条件、押した直後の結果、選択／実行、再入力 |
| 確定と復帰 | draftと確定、取消、戻る、保持・破棄する内容、focus・scrollの復元 |
| ゲームへの影響 | 時間・HP・所持・装備・フラグ・乱数・保存への影響を担当仕様へリンク |
| 使用不可と失敗 | 理由、修正・再試行、待機、失敗時の状態保持 |
| 構図と内容条件 | 基準寸法、固定／伸縮領域、長文・最大桁・欠損・小画面・文字拡大の扱い |
| 資料と例外 | 原画像の役割、Figmaの対象版、共通契約で不足する理由と比較根拠 |
| 確認方法 | 対象状態の実画像、視覚レビュー、一致検証、操作保証の担当層、未確認点 |

各操作を「押せる」「既存へ接続する」で済ませない。少なくとも次の関係を一行で追えるようにする。

| 操作／入力 | 条件と直後の結果 | 確定・取消・戻る | 保持／変更と仕様 | focus・失敗 |
| --- | --- | --- | --- | --- |
| 対象操作 | 状態と意味入力 | 反映点・出口・再入力 | 正本へのリンクと対象 | 入力先・復元先・再操作 |

## 仕様と画面の境界

表示する情報は、その画面で行う判断に対応させる。静的な場所選択、動的な会話、購入、編成、保存確認は目的と確定点が異なる。接続先が存在することは、その画面まで制作する許可ではない。

画面を開く、選択する、活動を始める、購入する、完了する、保存するという異なる出来事を区別する。画面移動のために消費や時間進行を加えない。詳細は[本編導線](../specs/overview.md)、[時間](../specs/time.md)、[物品](../specs/items.md)、[編成](../specs/party.md)、[会話](../specs/adventure.md)、[保存](../specs/save.md)へ対応付ける。

既存ゲーム仕様と新要求に矛盾があれば、具体的な入力と結果を確認する。見た目の変更へゲーム規則の変更を混ぜず、実装時に不足操作を即興で追加しない。設定未決の場所・人物・機能を、仮コンテンツから決定済みにしない。

## 設計を確かめる例

| 案・状況 | 判断と必要な確認 |
| --- | --- |
| 新しい背景に旧UIを載せる | 各要素の判断上の必要性、操作結果、階層を説明できるか。旧配置を残しただけでは設計完了にならない |
| 同格の入口を全て同じ図案にする | 一貫性だけでなく、異なる対象を識別できるか。機能と外観の両方向を照合する |
| 大きい部品を小さいラベルへ流用する | familyの役割、文字と図案の関係、強調の理由が成立するか |
| 文字を減らして操作不可理由まで消す | 何をすれば操作可能になるか理解できるか。必要な情報の欠落へ戻す |
| 通常画像だけで全状態を完成にする | focus、押下、不可、最大桁、長文、拡大、小画面等の該当条件が未確認 |
| CSS値が揃ったので美観を合格にする | 実画像で字面・図案・余白・群の関係を確認する。値の一致は視覚レビューの代用にならない |

背景差替えだけが指定された保守作業は、その範囲と既存設計で判断する。構成を再設計する依頼へ、限定保守の扱いを流用しない。
