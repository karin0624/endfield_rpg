# テスト設計

今回の追加・削除代替・破壊による検証例は [変更の検証記録](testing/change-evidence.md) にまとめる。

## 何をどこで保証するか

仕様の正本は `specs/`、具体的な入力と独立した期待結果はテストコードに置く。仕様・テスト・assertionを別の巨大台帳へ転記しない。実装済み仕様はすべてテストする必要があるが、coverage率、関連テストの存在、成功件数だけで仕様の充足を証明したとは扱わない。変更する受入条件と境界をPRで具体的なテスト名・assertionへ対応付け、未対応・未監査・矛盾・将来未実装を区別してレビューする。

目視確認は開発中のデバッグ・デザインレビューでありテストではない。撮影・録画・overlay出力も自動VRTの成功とは区別する。

| 責務 | 技術と具体例 |
| --- | --- |
| 静的な整合性 | TypeScript・Biome。型や構文を確認する |
| 純粋な規則 | Vitest。乱数0.5と命中率0.5の一致で外れる、持込み3個が各消費後2→1→0になってから獲得分を使う |
| ドメインの接続 | Vitest。実際の `actInExpedition` で回復7→敵被弾4→3、最終HP13・RNG1・バッグ1を独立した期待値でassertする。探索→帰還→保存復元も検証する |
| 公開I/Oの接続 | Vitest＋実HTTP。保存APIの409/413/500と失敗時の旧保存保持。mockの呼出回数だけで保存成功とはしない |
| ブラウザ内の接続 | Playwright。本番campaign祖先captureを通る選択→押し直し解除、各着弾のHP、速度／省略／離脱後の論理状態・RNG。独自に呼出順を構成するfixtureは表示・入力の保証として扱う |
| 描画・実資源 | Playwright＋実Babylon.js/WebGL。資源解放、HTTP取得回数、culling、配置。仕様化された回数は意味ある契約として維持する |
| 通常配布の代表経路 | Playwright。タイトル→探索→帰還→保存再開とデバッグ起動禁止。fixtureや専用デバッグビルドと区別する |

VRTはブラウザ各層で使う**視覚assertion**であり、万能な独立層ではない。編成の枠・番号・押下/focus・disabled、設定保存後の実会話、通常版10状態を `toHaveScreenshot` で比較する。色やCSS変数だけのassertionで見た目を保証しない。aria属性、focus、公開保存形式は観測可能な意味があり、内部値という理由で削除しない。

### Coverageの使い方

Vitest 5の標準 `@vitest/coverage-v8` を使用する。`coverage.include` に `src/**/*.ts` と `scripts/*.{ts,mjs}` を明示し、テスト自身を除外する。既定の「importされたファイルだけ」の分母で未読込実装を隠さない。`coverage/unit/` のHTML・LCOV・JSONを確認する。描画や起動コードの不足はブラウザで担う責務と照合し、率を上げるためだけにunitへ複製しない。

Coverageは実行箇所の探索手段であり、assertionの有無・十分性や自然言語仕様の完全性は測らない。両側の分岐を通っても `<` と `<=` の違いは境界入力がなければ検出できず、CSSが実行されても見た目は保証されない。未実行行・分岐は、具体的な仕様条件と照合して不足を補う。単純な全体率の閾値を根拠なく輸入しない。ゲーム規則は今回の実測（行97.09%、文95.31%、関数100%、分岐93.41%）を基に、標準設定で行97・文95・関数100・分岐93%を下限とする。これは現状からの低下を検知する下限であり、仕様網羅の達成値ではない。下限や除外対象の変更には理由とテスト差分のレビューが必要で、自動更新しない。テスト削除、対象除外、実装削除による分母の変化もレビューする。

### ブラウザcoverageと通常配布の区別

`npm run test:coverage` は既存PlaywrightのChromium V8 coverageを収集し、`monocart-coverage-reports` でHTML・LCOV・JSONへ変換する。既存実例は [Mermaidの収集処理](https://github.com/mermaid-js/mermaid/blob/97b345154f2cd71f23a2aadb14af6dad46f63173/e2e/helpers/coverage.ts)。このリポジトリでは一時コピーから動く設定サーバーのパスをrepo相対の `src/` へ正規化し、未読込の実装も標準 `all` 設定に含める。テスト・型宣言・依存ライブラリ・CSSの開発用JSラッパーは対象外にする。自前のcoverage計算器は持たない。

- 通常の `npm run test:e2e` は通常配布ビルドを検証する。coverage用の実行とは独立したCI結果を残す。
- 分析専用ビルドは `COVERAGE_BROWSER=1` でinline source mapを付け、minifyを無効にする。`dist-coverage` / `dist-debug-coverage` を使い、通常配布の出力を置き換えない。
- `coverage/browser/{built,debug,ui,settings}/` を別々に出力する。同じソース一覧を対象にしても、buildのtree shakingと開発サーバーでは実行可能行の分母が異なる。例えば試験時の `partyUi.ts` は非圧縮buildで175行、fixtureで185行だった。unitのAST remapとブラウザのbranch mapも同一とは限らず、率の平均や未検証の結合はしない。
- `tests/e2e/coverage.ts` の標準page fixtureからテストをimportする。追加pageや明示contextが必要な場合は収集経路も整える。Biomeの既存import制約で素のtestによるfixture迂回を検出する。
- `resetOnNavigation: false` だけでは再読込前の命中が失われることを実測した。再読込・2回目以降の文書遷移の直前に `collectCoverage(page)` を呼び、回収してから再開する。HTTP文書遷移の回収漏れ、必要なsource map不足、project全体の収集なしを失敗にする。

仕様ID台帳を必須にしないのは、この規模で仕様とassertionを重複管理する保守費用を避ける設計判断であり、公式ツールがあらゆる案件へ定めた規則ではない。coverageもレビューの代わりにはしない。

### 変更からマージまで

1. 仕様・公開API・実装差分から前提、入力、期待結果、拒否条件、通常の往復操作、境界を洗い出す。既存実装の挙動を正解として仕様を狭めない。
2. 適切な層で具体的なassertionを追加／修正する。テスト名とdescribeで条件を明確にする。必要ならissue annotationを付けるが、手書きIDやassertion転記を必須にしない。削除するテストは同じ保証の代替先をPRに示す。
3. `npm run check` と固定コンテナの `npm run test:e2e` を実行する。通常CIは built/debug/ui/settings **すべて**を実行する。各projectの `tests/e2e/<project>/**/*.spec.ts` をglobで収集し、ファイルごとの登録は不要にする。開発用の部分実行は全体確認の代わりにしない。onlyは禁止し、品質テストのskip/todoや結果欠落を成功に数えない。録画専用の `tests/evidence/battle-video.spec.ts` は別設定で実行する。
4. 標準runnerの実行結果とcoverageを確認し、テストファイルの未発見、ケースの未実行、不安定な再試行を確認する。 `scripts/check-test-execution.mjs` はgit管理対象のテストファイルと、標準CLIの収集JSON・実行JSONを照合する。runnerにはskipを一律失敗にする共通設定がないため、未発見ファイル・結果欠落・skip/todo・期待された失敗・retryを拒否するこの小さな補助を置く。手作業のケース一覧や仕様判定は持たない。Vitest 5の収集は `list --no-static-parse` でパラメータ展開後を使用する。受入条件全体を満たすassertionの十分性と未記述の仕様は差分レビューで判断する。
5. VRT基準は自動承認しない。画像を開いて入力・内容・差分理由を確認した後、更新なしでも比較する。通常実行は `updateSnapshots: "none"` とし、更新は明示的に行う。
6. 最初から通常PRを作り、マージ前に既存保証／今回追加／削除代替／残る未検証を具体例と層で説明する。正確な最終headと統合先baseの組、CI結果を確認してマージ担当が判断する。先行PRやbaseの更新後は統合結果を再確認する。

[工程・権限の境界](testing/review-controls.md)も参照する。mainの保護・required checksが未設定のため、CIだけで書込権限者のマージを強制的に止めることはできない。設定／プラン変更はこの作業の範囲外である。

標準機能の根拠: [Vitest coverage](https://vitest.dev/guide/coverage.html)、[coverage設定](https://vitest.dev/config/coverage)、[Playwright coverage](https://playwright.dev/docs/api/class-coverage)、[Playwright CLI](https://playwright.dev/docs/test-cli)。以下は領域別の具体例であり、日付付き監査記録を日常運用の第二の仕様正本にはしない。

ゲームのルール、画面の見た目、操作から結果までの接続を、それぞれ最も安定して検証できる場所で担保する。ブラウザテストはChromiumに絞る。

テストは仕様で約束した公開の操作と、その利用者が観測できる結果を検証する。ゲーム本体では定義データと公開操作から状態を作り、仕様にあるHP・行動順・勝敗・イベント・拒否理由などを見る。画面では実際の入力から表示、ダウンロード、保存結果を見る。必要な期待値は仕様の例や独立した具体例から決め、検証対象と同じ処理や計算で作らない。実行結果をもう一度同じ処理で作った結果と比較するだけのテスト、通常の操作では作れない内部状態、内部の配列形状・参照同一性・素材ファイル名を成功条件にしない。内部の変更で壊れたときに利用者の振る舞いへ影響がないアサーションは削る。

UI変更の見た目は[完成画像承認と直接画像比較の必須ゲート](ui-asset-production.md#ui開発の必須ゲート)で確認する。承認済みfixture・同一解像度の実画面・50%overlay・マスクなし全体pixel diff・事前承認領域とその他UI領域の別集計をPRへ保存し、画像自体を開いて検査する。既存実装から作ったVRT基準への一致、機能テスト成功、寸法や説明文の比較は、ユーザーの承認画像への一致を証明しない。未説明・未合意の意味あるデザイン差や証跡不足はマージ不可とする。差分検出は閾値0、判定は意図しない差の有無で行い、完全画素一致を要求しない。フォントや既存立ち絵の微差は原因を記録し、全画面共通タイポグラフィ等の後続課題へ分けられる。

| 対象 | 方法 | 担保すること |
| --- | --- | --- |

描画の寿命テストは同じ環境の再読込を避ける性能契約と、ブラウザのWebGL資源作成・削除を観測する。複数回切り替えても使用中のbuffer・texture・program数が増えず、探索退出相当の破棄で全て削除されることを確認する。この数はネイティブ資源の所有状態であり、GPUメモリの使用量ではない。表示と操作の結果も同時に確認し、資源数だけを成功条件にしない。

地形の裏面カリング回帰は`npm run test:editor`で確認する。既定PC／モバイルと小移動範囲の四隅は確認済み画像を使い、地形内部・未検証構図・未検証環境・同じパスの別内容・照合不可は元材質の画像と完全一致を確認する。適用／プレビューと環境切替で範囲内外を往復し、カリング復帰も確認する。素材差替えの試験はHTTP応答のGLBメタデータだけを変え、正規素材と形状・材質を変更しない。読込保留中に環境が終了した場合は、遅着した地形のimportを始めず、現環境の表示と資源解放を保つ。

この最適化の対象は、読み込むバッファを環境ごとに一度SHA-256で照合したGLBと、`groundCulling.ts`の限定構図である。高さだけで任意視点を安全と判断しない。範囲や素材を広げる場合は、元材質とのピクセル差、人物の接地・地形の輪郭、通常演出を固定コンテナで比較し、画像をレビューする。基準画像の更新は確認済みのカリング差に限定し、既存VRTの許容差は変更しない。

戦闘UIのfixtureは`tests/fixtures/battle-ui.html`に隔離し、配布ビルドや製品の起動パラメータには追加しない。ダンジョンの初期状態は本番定義と公開コア操作で作り、以後は実入力を本番UIから`actInExpedition`へ渡す。代替rendererが担当するのは敵の表示座標、演出完了、描画表示の初期化・破棄だけで、HP・勝敗・スキル・精神疲労・行動順は代替しない。このfixtureの座標は実投影の正しさを保証しない。実投影・素材・WebGL資源の確認は配布画面と描画の寿命テストが担う。

| 検証する公開入力と結果 | 検証層／ケース | WebGL側に残す保証 |
| --- | --- | --- |
| 敵を選ぶと選択が切り替わり、通常攻撃で対象HPが6/14になる | `ui`：敵を選んで攻撃すると対象のHPが更新される | 通常モーションの攻撃と撃破後の配置 |
| 攻撃で敵が消え、勝利・入力停止・再戦によるHPと選択の復元ができる | `ui`：実ボタンから勝利し、再戦で初期状態へ戻る | 実描画での通常モーション、再戦、再読込 |
| スキル予測16と選択対象、Esc／戻るのfocus復帰、取消後の疲労0、使用後の疲労0→4→7 | `ui`：スキルの予測・取消・使用から実コアの結果を表示する | 通常探索の必須3択後に分岐回復、次戦で疲労14・成長反映後の予測14.91、帰還時22、保存再開、街回復後12の引継ぎ |
| 320・390・900・901・1440・1920px幅と短い画面でのボタン到達・横はみ出しなし、回復対象の選択と取消 | `ui`：スキルの予測・回復対象・取消を各画面サイズで操作できる | 390pxの実戦闘スクロール操作、実投影のリサイズ、PC／モバイルVRT |

各保証を対応する層で確認し、UIの画面寸法ごとに地形を再描画して同じ操作を重複検証しない。`npm run test:ui`は固定コンテナ内でこのUI層だけを実行し、配布ビルドを必要としない。通常CIの`npm run test:e2e:inside`は`built`・`debug`・`ui`・`settings`を同じworkers設定で実行する。fixtureは設定保守テストと同じ隔離されたソース用サーバーから提供する。

静止画で確認できる要素の存在・配置を個別のDOMアサーションで重複させない。画像に写らない状態変化や操作の意味は画像比較に任せない。生活ループはNodeで単独開始から分岐、勝利／全滅、帰還、療養、加入、再探索、保存復元まで同じ状態を渡して確認する。基礎最大HP200・命中率80%の連続症状効果、生活半日と療養回数、乱数と重複抑止はNodeが担う。ブラウザでは通常の街起動の代表経路と、数値回復の表示・保存再開を実操作で確認し、戦闘ルールの分岐を網羅しない。`page.evaluate`で戦闘状態を直接変更せず、ゲーム本体と本番の入力経路を使う。

VRTの基準画像はPlaywrightのバージョンを固定した公式コンテナ内で生成し、同じ環境のCIで比較する。Chromiumのソフトウェア描画、画面寸法、device scale、視差効果の設定を固定する。基準画像はレビューしてから更新し、差分を許容する設定で大きな欠損を隠さない。描画の準備完了だけで成功とせず、実際の画像比較、素材のHTTPエラー、ページエラーも確認する。WebGLが使えない場合は失敗として報告する。

ローカルからは`npm run test:e2e`または`npm run test:editor`がコンテナを起動する。コンテナ外でPlaywrightを直接起動した場合は設定の読み込み時に失敗させる。CIのコンテナジョブは`npm run test:e2e:inside`を使う。基準画像更新時のコマンドは[README](../README.md)を参照する。

各E2Eケースは独立した初期画面から始める。症状の表示ケースでは、試験開始時だけ公開コア操作と保存形式から初期データを準備し、その読込後は通常のボタン・キー入力だけで進める。途中でHP、症状、勝敗、時間を注入して成功としない。通常の`test:e2e`では`prefers-reduced-motion: reduce`を指定して移動演出を省き、静止表示の読み取り時間後の確定結果を確認する。描画更新の回帰では、限定した通常モーションのケースで攻撃・撃破・再戦・再読込後の操作と配置も確認する。待機はPlaywrightの再試行付きアサーションで画面の状態変化を待ち、固定秒数のsleepを使わない。可視範囲は`toBeInViewport()`、位置変化は`expect.poll(() => locator.boundingBox())`などのLocator APIで確認し、DOM計測だけを目的に`page.evaluate`やrequestAnimationFrameで待たない。アニメーションの見た目を検証する必要が生じた場合は、静止画VRTとは分けて安定した観測方法を設計する。失敗時はスクリーンショットとトレースを保存する。`npm run check`ではブラウザを起動せず、CIのブラウザジョブは全projectの登録済みケースを実行する。

リサイズ前から有効な攻撃ボタンは、敵札・マーカーのレイアウト完了の根拠にならない。表示側はステージ・敵札・マーカーの寸法変更を監視し、予約した1フレームで現在の投影位置と実寸を使って配置する。札・マーカーだけの寸法変更では投影とDOM配置を更新し、地面を描き直さない。canvasの実描画寸法変更は次の描画フレームへまとめる。この性能契約はブラウザのWebGL draw呼出を観測して確認し、同時に実際の札とマーカーの配置を検証する。静止中の連続再描画は追加せず、画面離脱では予約フレームと監視を解放する。リサイズ回帰は変更前との幅の不一致ではなく、指定した画面サイズに対応する16:9のステージ寸法と、札・マーカーの位置関係を同時に確認する。ソフトウェア描画で測定自体が遅れる場合も表示準備と同じ60秒の範囲で待ち、途中の値を成功条件にしない。モバイルVRTの不一致を調べる場合は、投影位置、ステージ寸法、敵札の幅・高さ、マーカー位置を撮影前後に記録する。撮影時に札の固有寸法だけが変わる場合、固定sleepや許容差変更で隠さず、寸法変化の原因と表示側の更新契約を先に調べる。単発の成功を安定性の証明にしない。

編成候補の多人数表示は`tests/fixtures/party-selection.html`の12人／24人で確認する。人数と追加の名前は表示条件であり本編の加入候補には追加しない。`ui`プロジェクトで候補のキーボード移動、詳細からの編集枠・候補・スクロール・focus復帰、連続入力の各結果と詳細閲覧時の状態不変、確定一回、狭幅・低い画面・長名・未提供素材を確認する。実キャラの顔は採用済み2人の素材だけを使うため、多数の異なる顔の識別性の検証にはならない。

成長の試用経路は勝利XP→複数3択→次戦→帰還初期化→保存再開を通常入力で確認する。Nodeでは街XPの持込み、報酬再送、レベル余剰、全97通りの試用3選択経路、HP増分・HP0・控え初期化・古い選択の拒否・現行保存形式の検証を担当する。描画代替UIでは必須選択の表示とスクロール／キーボード到達性を確認し、WebGL側には実素材を使う次戦・帰還の経路を残す。旧保存の移行は行わず、非対応として拒否して既存スロットを保持する。

追加発症はNodeで使用前の効果と使用後の確率を分け、当該負荷だけの付与量、重度後の悪化、上限候補除外、空候補の乱数不消費、成長HP差分、旧保存拒否を検証する。UIでは実コアの高疲労fixtureからスキルを使い、ゲージ下アイコンのキーボード・タッチでの説明表示と、重度のまま数値が悪化する結果を確認する。

分岐回復はNodeで独立した初回・次回の数値期待、固定乱数による発症・非発症、上限候補除外、自己回復後のHP制限、再送・古い画面・帰還後・再出撃・必須選択の拒否と時計・成長・控え不変を確認する。UIでは使用者・技・対象の実選択、取消とEsc、フォーカス復帰、320／390pxを含む狭幅、同じ分岐での意図的再使用を検証する。

## 受入条件のレビュー

実装済みの全仕様を、公開入力・前提・観測結果に分け、仕様の参照箇所から具体的なテストファイル・ケース名・assertionへ対応付ける。似た名前のテスト、成功件数、カバレッジ率だけでは対応済みにしない。仕様一覧とテスト対応の全体監査が未完了なら、未テスト箇所がないとは報告しない。

- PRでは変更した条件の仕様参照、入力・期待結果、テスト名と層、残る不足を簡潔に示す。テスト内にある期待値を全件別台帳へ転記しない。未実装の計画を実装済み仕様へ混ぜない。
- 目視、手元操作、スクリーンショット撮影、artifact保存、レビュー用diffは開発中の確認・証跡であり、自動テストのcoverageではない。見た目の契約はレビュー済み基準に対する自動VRT等へ接続し、操作の契約は入力→観測結果の自動assertionで検証する。
- 仕様を実装・変更するPRでは受入条件の説明を更新し、各変更仕様のテストとassertionを必須にする。既存仕様でも不足・未監査が判明したら記録し、適切な層のテストを追加する。仕様にテストが未対応のまま、目視確認やCI成功で埋め合わせてマージしない。
- 不具合の再現・既知の不足では、元の不具合や妥当な破壊を入れた場合に対象テストが失敗することを確認する。一時的な破壊は復元し、対象・失敗したassertion・復元後結果を残す。全テストへ機械的な変異試験を追加するという意味ではない。
- コードレビューは実装差分だけでなく仕様・入力経路・assertion・不足一覧を確認する。全体監査から未テスト仕様が見つかった場合は、個別不具合のテスト追加だけで再発防止完了としない。

## 操作仕様と入力経路のレビュー

UI操作を変更するPRは、受入仕様・テスト名（ファイルとケース名）・検証層を対応付ける。状態関数のテストだけで「クリックで切り替わる」を検証済みにしない。選択→同じ対象を押し直して解除は通常の往復操作で、特別な速度試験ではない。

- 状態の更新規則は単体で、実入力から更新への接続は実際にmountしたUIで検証する。子のhandlerだけでなく、通常画面の親capture／bubble、dialog、focus、画面切替後の入力先まで含める。
- 連続押下を検証する際、別々のPlaywright `.click()` は各 `detail=1` になるため、同一入力列の保証にはしない。mount済UIにmousedown/up/clickの `detail=1→2→3` を同期dispatchするintegrationと、native pointer／double-clickのブラウザ試験を使い分け、各入力直後の観測結果を確認する。
- 必要なロード／画面準備完了は待ってよい。仕様にないsleep、cooldown終了待ち、操作間のretry assertionを入れて通常の選択／解除を通さない。非同期完了を待つ場合は対象の契約と待つ理由をPRに示す。
- guard／throttle／debounceの追加・既存流用は、抑止する操作と理由、許可する通常操作、配置した祖先、画面遷移後の影響をレビューする。二重実行防止は確定・出発・保存・遷移等の対象操作に限定し、画面全体の既定抑止＋候補例外を採用しない。選択や数量入力は通常の入力を1回ずつ受け取る。編成／campaignは対象ボタンへ `data-single-activation` を明示し、見た目のクラスを抑止条件にしない。購入処理は購入ボタン自身の既存ガードを維持する。
- レビューはdiffの局所だけでなく変更した操作が通る親まで読み、テストが実際に送るイベントを確認する。バグ修正では修正前に失敗し修正後に通る回帰を確認する。画像・機能テストの成功件数だけで仕様の網羅を代用しない。

## 通常版とデバッグ版の起動境界

`test:e2e` は通常ビルド（4173、`built`）、専用デバッグビルド（4175、`debug`）、描画代替fixture（4174、`ui`）を分ける。通常版の `campaign.spec.ts` で新規開始・仮導入・街・編成・探索・戦闘・帰還・保存再開、無消費の移動、保存失敗、既存保存保持、URL改変によるデバッグ混入がないことを確認する。従来の街起動・直接探索・固定戦闘デモの詳細回帰は明示デバッグURLを使い、通常版の通し検証の代わりにしない。デバッグ側の保存テストは独立キーを使う。既存戦闘VRTの基準画像名は継続して使う。

本編通しE2Eは1920×1080でタイトル、新規確認、仮導入、ホーム、探索先、街、帰還後ホーム、保存確認、保存後タイトル、再開後ホームの10状態を自動VRT比較し、画像artifactも保存する。自動比較成功と画像レビューを別々に報告する。ブラウザBack/Forwardは通常配布でデバッグ指定URLを往復し、タイトル・通常モード・保存保持を確認する。

物品は通常版で市場購入・持込み・分岐回復・帰還・保存、共有装備の排他割当てとHP非回復を検証する。戦闘表示fixtureでは実コアの物品消費から回復8→敵被弾4の順序、疲労不変、入力連打・演出省略でも確定一回、誤った勝敗演出がないことを確認する。
