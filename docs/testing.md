# テスト設計

ゲームのルール、画面の見た目、操作から結果までの接続を、それぞれ最も安定して検証できる場所で担保する。ブラウザテストはChromiumに絞る。

テストは仕様で約束した公開の操作と、その利用者が観測できる結果を検証する。ゲーム本体では定義データと公開操作から状態を作り、仕様にあるHP・行動順・勝敗・イベント・拒否理由などを見る。画面では実際の入力から表示、ダウンロード、保存結果を見る。必要な期待値は仕様の例や独立した具体例から決め、検証対象と同じ処理や計算で作らない。実行結果をもう一度同じ処理で作った結果と比較するだけのテスト、通常の操作では作れない内部状態、内部の配列形状・参照同一性・素材ファイル名を成功条件にしない。内部の変更で壊れたときに利用者の振る舞いへ影響がないアサーションは削る。

| 対象 | 方法 | 担保すること |
| --- | --- | --- |
| ゲーム本体と描画に依存しない計算 | Node環境のVitest（`npm run check`） | 仲間一覧・1〜4人PT・控え・編成拒否・出撃と退出のHP／フラグ引継ぎ、行動順、攻撃、HP、勝敗、再戦、固定ダンジョンの接続・解決・引き継ぎ、設定値の検証・移行、隊列計算。実時間やブラウザを使わず分岐を確認する |
| 静的な見た目 | 固定コンテナ内のPlaywright VRT（`npm run test:e2e`） | 実際のBabylon.js、WebGL、GLB・PNGを読み込んだ初期戦闘画面を代表的な画面幅で画像比較する |
| 戦闘UIと実コアの接続 | 描画だけを代替するPlaywright（`npm run test:ui`、`npm run test:e2e`にも含む） | 本番の戦闘UIとゲーム本体を使い、実ボタンでの対象選択、攻撃、HP更新、勝利、再戦、スキル予測・取消・使用結果・回復対象・focus復帰を確認する。複数画面寸法で使用／戻るボタンに到達でき、横方向にはみ出さないことを確認する |
| WebGLを含む操作・接続 | 配布ビルドのPlaywright（`npm run test:e2e`） | 実素材、投影・リサイズ、通常モーション、街から探索して戦闘・帰還する代表経路と、次戦・帰還・保存読込・街回復へ精神疲労が引き継がれることを確認する |
| 編成画面 | Playwrightの挙動アサーション（`npm run test:e2e`） | 編成画面の開閉・キーボード操作・戻った後の編集保持、4枠編集、候補の未確定選択・確定・取消、空編成・重複の拒否表示、単独出撃、探索の成功／失敗と街に戻ったHPを実入力で確認する |
| キャラ詳細 | Playwrightの挙動アサーション（`npm run test:e2e`、表示条件は`npm run test:editor`） | 実名・能力・症状、読込／帰還後の現在値、読み取り専用の保存内容不変、Esc／戻るのfocus復帰を確認する。隔離した公開UIの表示条件で長い名前・複数症状・未提供画像を確認し、本編の仲間を増やさない |
| ダンジョン画面 | Playwrightの挙動アサーション（`npm run test:e2e`） | 戦闘・会話ノードの入力、終了後のルート復帰、横ドラッグとリサイズ後の選択、390px表示の分岐配置と戦闘コマンドのスクロール操作を確認する |
| 構図設定の保守 | 必要時だけ実行するPlaywright（`npm run test:editor`） | 戦闘と会話の設定画面のVRT、編集・保存・復元、保存APIを確認する。通常のCIには含めない |
| 戦闘描画の寿命 | 描画の変更時に実行するPlaywright（`npm run test:editor`） | 隔離した公開描画・UIで人数・同一IDを含む次戦切替、旧演出や旧ハンドルの無効化、未完了の読込中の環境切替・退出、二重破棄を確認する。通常CIの探索経路と併せて検証する |

描画の寿命テストは同じ環境の再読込を避ける性能契約と、ブラウザのWebGL資源作成・削除を観測する。複数回切り替えても使用中のbuffer・texture・program数が増えず、探索退出相当の破棄で全て削除されることを確認する。この数はネイティブ資源の所有状態であり、GPUメモリの使用量ではない。表示と操作の結果も同時に確認し、資源数だけを成功条件にしない。

地形の裏面カリング回帰は`npm run test:editor`で確認する。既定PC／モバイルと小移動範囲の四隅は確認済み画像を使い、地形内部・未検証構図・未検証環境・同じパスの別内容・照合不可は元材質の画像と完全一致を確認する。適用／プレビューと環境切替で範囲内外を往復し、カリング復帰も確認する。素材差替えの試験はHTTP応答のGLBメタデータだけを変え、正規素材と形状・材質を変更しない。読込保留中に環境が終了した場合は、遅着した地形のimportを始めず、現環境の表示と資源解放を保つ。

この最適化の対象は、読み込むバッファを環境ごとに一度SHA-256で照合したGLBと、`groundCulling.ts`の限定構図である。高さだけで任意視点を安全と判断しない。範囲や素材を広げる場合は、元材質とのピクセル差、人物の接地・地形の輪郭、通常演出を固定コンテナで比較し、画像をレビューする。基準画像の更新は確認済みのカリング差に限定し、既存VRTの許容差は変更しない。

戦闘UIのfixtureは`tests/fixtures/battle-ui.html`に隔離し、配布ビルドや製品の起動パラメータには追加しない。ダンジョンの初期状態は本番定義と公開コア操作で作り、以後は実入力を本番UIから`actInExpedition`へ渡す。代替rendererが担当するのは敵の表示座標、演出完了、描画表示の初期化・破棄だけで、HP・勝敗・スキル・精神疲労・行動順は代替しない。このfixtureの座標は実投影の正しさを保証しない。実投影・素材・WebGL資源の確認は配布画面と描画の寿命テストが担う。

| 検証する公開入力と結果 | 検証層／ケース | WebGL側に残す保証 |
| --- | --- | --- |
| 敵を選ぶと選択が切り替わり、通常攻撃で対象HPが6/14になる | `ui`：敵を選んで攻撃すると対象のHPが更新される | 通常モーションの攻撃と撃破後の配置 |
| 攻撃で敵が消え、勝利・入力停止・再戦によるHPと選択の復元ができる | `ui`：実ボタンから勝利し、再戦で初期状態へ戻る | 実描画での通常モーション、再戦、再読込 |
| スキル予測16と選択対象、Esc／戻るのfocus復帰、取消後の疲労0、使用後の疲労0→4→7 | `ui`：スキルの予測・取消・使用から実コアの結果を表示する | 通常探索の必須3択後に分岐回復、次戦で疲労14・成長反映後の予測14.91、帰還時22、保存再開、街回復後12の引継ぎ |

各保証を対応する層で確認し、UIの画面寸法ごとに地形を再描画して同じ操作を重複検証しない。`npm run test:ui`は固定コンテナ内でこのUI層だけを実行し、配布ビルドを必要としない。通常CIの`npm run test:e2e:inside`は配布画面の`built`と描画代替の`ui`を同じworkers設定で実行する。fixtureは設定保守テストと同じ隔離されたソース用サーバーから提供する。

静止画で確認できる要素の存在・配置を個別のDOMアサーションで重複させない。画像に写らない状態変化や操作の意味は画像比較に任せない。生活ループはNodeで単独開始から分岐、勝利／全滅、帰還、療養、加入、再探索、保存復元まで同じ状態を渡して確認する。基礎最大HP200・命中率80%の連続症状効果、生活半日と療養回数、乱数と重複抑止はNodeが担う。ブラウザでは通常の街起動の代表経路と、数値回復の表示・保存再開を実操作で確認し、戦闘ルールの分岐を網羅しない。`page.evaluate`で戦闘状態を直接変更せず、ゲーム本体と本番の入力経路を使う。

VRTの基準画像はPlaywrightのバージョンを固定した公式コンテナ内で生成し、同じ環境のCIで比較する。Chromiumのソフトウェア描画、画面寸法、device scale、視差効果の設定を固定する。基準画像はレビューしてから更新し、差分を許容する設定で大きな欠損を隠さない。描画の準備完了だけで成功とせず、実際の画像比較、素材のHTTPエラー、ページエラーも確認する。WebGLが使えない場合は失敗として報告する。

ローカルからは`npm run test:e2e`または`npm run test:editor`がコンテナを起動する。コンテナ外でPlaywrightを直接起動した場合は設定の読み込み時に失敗させる。CIのコンテナジョブは`npm run test:e2e:inside`を使う。基準画像更新時のコマンドは[README](../README.md)を参照する。

各E2Eケースは独立した初期画面から始める。症状の表示ケースでは、試験開始時だけ公開コア操作と保存形式から初期データを準備し、その読込後は通常のボタン・キー入力だけで進める。途中でHP、症状、勝敗、時間を注入して成功としない。通常の`test:e2e`では`prefers-reduced-motion: reduce`を指定して演出の待ち時間を省き、確定後の結果を確認する。描画更新の回帰では、限定した通常モーションのケースで攻撃・撃破・再戦・再読込後の操作と配置も確認する。待機はPlaywrightの再試行付きアサーションで画面の状態変化を待ち、固定秒数のsleepを使わない。可視範囲は`toBeInViewport()`、位置変化は`expect.poll(() => locator.boundingBox())`などのLocator APIで確認し、DOM計測だけを目的に`page.evaluate`やrequestAnimationFrameで待たない。アニメーションの見た目を検証する必要が生じた場合は、静止画VRTとは分けて安定した観測方法を設計する。失敗時はスクリーンショットとトレースを保存する。`npm run check`ではブラウザを起動せず、CIのブラウザジョブは短い接続確認だけを実行する。

リサイズ前から有効な攻撃ボタンは、敵札・マーカーのレイアウト完了の根拠にならない。表示側はステージ・敵札・マーカーの寸法変更を監視し、予約した1フレームで現在の投影位置と実寸を使って配置する。札・マーカーだけの寸法変更では投影とDOM配置を更新し、地面を描き直さない。canvasの実描画寸法変更は次の描画フレームへまとめる。この性能契約はブラウザのWebGL draw呼出を観測して確認し、同時に実際の札とマーカーの配置を検証する。静止中の連続再描画は追加せず、画面離脱では予約フレームと監視を解放する。リサイズ回帰は変更前との幅の不一致ではなく、指定した画面サイズに対応する16:9のステージ寸法と、札・マーカーの位置関係を同時に確認する。ソフトウェア描画で測定自体が遅れる場合も表示準備と同じ60秒の範囲で待ち、途中の値を成功条件にしない。モバイルVRTの不一致を調べる場合は、投影位置、ステージ寸法、敵札の幅・高さ、マーカー位置を撮影前後に記録する。撮影時に札の固有寸法だけが変わる場合、固定sleepや許容差変更で隠さず、寸法変化の原因と表示側の更新契約を先に調べる。単発の成功を安定性の証明にしない。

編成候補の多人数表示は`tests/fixtures/party-selection.html`の12人／24人で確認する。人数と追加の名前は表示条件であり本編の加入候補には追加しない。`ui`プロジェクトで候補のキーボード移動、詳細からの編集枠・候補・スクロール・focus復帰、連打と取消の状態不変、確定一回、狭幅・低い画面・長名・未提供素材を確認する。実キャラの顔は採用済み2人の素材だけを使うため、多数の異なる顔の識別性の検証にはならない。

成長の試用経路は勝利XP→複数3択→次戦→帰還初期化→保存再開を通常入力で確認する。Nodeでは街XPの持込み、報酬再送、レベル余剰、全97通りの試用3選択経路、HP増分・HP0・控え初期化・古い選択の拒否・現行保存形式の検証を担当する。描画代替UIでは必須選択の表示とスクロール／キーボード到達性を確認し、WebGL側には実素材を使う次戦・帰還の経路を残す。旧保存の移行は行わず、非対応として拒否して既存スロットを保持する。

追加発症はNodeで使用前の効果と使用後の確率を分け、当該負荷だけの付与量、重度後の悪化、上限候補除外、空候補の乱数不消費、成長HP差分、旧保存拒否を検証する。UIでは実コアの高疲労fixtureからスキルを使い、ゲージ下アイコンのキーボード・タッチでの説明表示と、重度のまま数値が悪化する結果を確認する。

分岐回復はNodeで独立した初回・次回の数値期待、固定乱数による発症・非発症、上限候補除外、自己回復後のHP制限、再送・古い画面・帰還後・再出撃・必須選択の拒否と時計・成長・控え不変を確認する。UIでは使用者・技・対象の実選択、取消とEsc、フォーカス復帰、320／390pxを含む狭幅、同じ分岐での意図的再使用を検証する。

`npm run check`、`npm run test:ui`、実素材の `npm run test:e2e` を使い分ける。通常UIの代表経路は既存 `dungeon.spec.ts` の加入・編成、成長・分岐回復・次戦・帰還・保存、全滅・療養を再利用し、全コアケースをブラウザへ複製しない。多段／複数対象は `multiAttack.test.ts` と `battle-ui.spec.ts` の独立した定義入力から製品runtime・実UIを検証する。本編catalogでの提供・取得経路の検証とは区別する。最終バランス、本番高レベルコンテンツ、ユーザー自身の試遊はこの自動検証の保証外。

短い手動確認では「同行者を探す（仮）」で加入し、編成の空き枠へ追加して出撃する。戦闘でスキルを使い、勝利後の3択をすべて選ぶ。分岐で回復を使ってからボスへ進み、帰還後の詳細でレベル・習得と疲労の違いを見る。街で保存・読込を行い、市場の会話を一回終えてから再出撃する。回復量と負荷の釣合い、3択で違う戦い方を選びたくなるか、街療養の待ち時間が長すぎないかは試遊時の観察点であり、テスト成功から面白さを判定しない。
