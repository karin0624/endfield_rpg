# テスト設計

## 基本方針

実装済みの仕様はすべてテストする。仕様の正本は `specs/`、公開の入力・前提・独立した期待結果はテストコードに置く。仕様やassertionを巨大な別台帳へ転記しない。目視確認は開発中のデバッグ・デザインレビューであり、テストではない。撮影・録画・overlayの生成も、自動VRTの成功とは区別する。

型検査、coverage率、似た名前のテスト、成功件数だけでは仕様の充足を証明できない。受入条件に対して、何を入力し、どの結果をどこでassertするかをレビューする。未対応・未監査・仕様矛盾・将来未実装を区別し、実装に合わせて期待を狭めたり、テストの不足を目視で埋め合わせたりしない。

同じ保証は、必要な境界を通る最も低コストの層で担う。規則の全組合せをブラウザへ複製しない。VRTはブラウザテストに置く**視覚assertion**であり、操作やゲーム状態を一括で保証する独立層ではない。

## 保証対象からテストを選ぶ

### 1. 静的な整合性

TypeScriptとBiomeで型、構文、依存、整形を確認する。実行時の入力や表示の正しさは次のテストで担う。

### 2. 個々の規則

Vitestでゲームの純粋な公開操作を検証する。確率の等値境界、値域、行動順、数量、無効入力などを、仕様から決めた具体的な期待値でassertする。実装定数から期待値を再計算しない。入力を変更しない契約では呼出し前のコピーと比較し、同じ参照同士の比較をしない。

### 3. ロジックの結合とゲームの内部状態のテスト

実際の複数機能を接続し、操作ごとのゲーム状態と副作用を確認する。探索→成長→帰還→保存復元、装備＋育成＋疲労、回復後の敵攻撃などは、ブラウザを起動しないVitestで担う。モデル／表示用ロジックの接続も、DOMや描画を必要としない公開境界で検証できるならこの層を選ぶ。

保存失敗でも旧データを保持する責務も、ここで公開保存境界へ入力を渡して確認する。API契約には実Vite/Node HTTPを使い、409の並行処理、413の入力上限、500の書込み失敗と保存先のbytesを検証する。HTTPは接続を再現する技術であり、保証対象を分ける独立した分類ではない。mockの呼出回数だけで保存成功やゲーム状態の不変を代用しない。

### 4. 入力から画面・状態への接続

Playwrightで実際にmountしたUIへボタン・キー・pointer入力を渡す。親capture／bubble、dialog、focus、画面切替後の入力先を通し、入力直後の選択・HP・ARIA・保存結果を確認する。選択→押し直し解除は普通の往復操作であり、特別な速度試験ではない。

描画だけを代替するfixtureは本番UIと実コアを使い、途中のHP・勝敗・RNGを注入しない。構図エディターの全control同期・draft・JSON出力は本番エディターと描画代替を接続し、重い地形判定を繰り返さない。代替rendererの座標は実投影の正しさを保証しない。

見た目の契約には、選択／解除、押下／focus／disabled、狭幅、保存後の実会話などの必要状態をVRT比較する。RGB、outline、CSS変数だけの比較を見た目の保証にしない。ARIA、focus、公開保存形式などの意味ある観測結果は維持する。

### 5. 実描画と資源の接続

Playwrightと実Babylon.js/WebGLで投影、素材、DPR、非rootのasset URL、配置、culling、画面離脱・pagehide・HMRを検証する。仕様化されたWebGL資源数やHTTP取得回数は有効な契約であり、内部値として一括削除しない。配置や素材の見た目はレビュー済み基準に対するVRTも使う。

### 6. 通常配布の境界と代表経路

通常buildで起動、通常入力、保存の導線、デバッグ機能・開発API・fixtureが配布へ混入しない境界を少数のPlaywrightケースで確認する。詳細な規則は低い層へ委ねる。

タイトル→導入→街→編成→戦闘→帰還→保存再開の長い代表経路と10状態のVRTは `tests/long/campaign.spec.ts` に保持し、`npm run test:long` で明示実行する。通常PR CIから外すが、削除・skipはしない。短い通常配布・入力・VRT境界、renderer/HMR/settingsの保証は既定CIに残す。

## 代表例

これは責務の選び方を示す例であり、全仕様を転記したcatalogではない。今回の既存保証・追加・削除代替・残件は [変更の検証記録](testing/change-evidence.md) を参照する。

| 受入条件 | 具体的な検出方法 |
| --- | --- |
| 命中率0.5では乱数0.5が外れる | Vitestの規則テストで等値の結果をassert。両分岐のcoverageが100%でも `<` と `<=` の違いは保証できない |
| 持込みを獲得分より先に消費する | Vitestで各消費後2→1→0、その次に獲得分が減ることをassert。4回後の最終値だけで済ませない |
| 回復7の後、敵被弾4と3が実行される | 実 `actInExpedition` を接続し、各出来事、最終HP13・RNG1・バッグ1を独立期待でassert |
| 保存が失敗しても旧保存を保つ | 実HTTPに不正・並行・上限入力や書込み失敗を渡し、応答と保存先の旧bytesをassert |
| 候補の押し直しが親captureに捨てられない | campaign配下のmount済UIと通常buildへ連続入力し、各入力直後の選択結果をassert。選択／解除のVRTで枠・番号の実表示も比較 |
| 表示速度・省略・退出で戦闘結果を変えない | Playwright Clockで表示時刻を制御し、着弾前後のHP、確定後の実論理状態とRNGをassert |
| 退出後にWebGL資源が残らない | 実rendererで読込・失敗・切替・退出を行い、資源が0になる完了条件をpoll。描画の配置はVRTで別に確認 |

## 実行と速度

Node.jsは `.nvmrc` の24系を使う。ブラウザは固定した `mcr.microsoft.com/playwright:v1.63.0-noble` と実LFS素材を使い、基準生成と比較の環境を揃える。ホストからは以下のscriptを使う。CIはコンテナ内の `:inside` を実行する。

| コマンド | 担当 |
| --- | --- |
| `npm run check` | Biome・型・Vitest・V8 coverage・発見／実行結果照合。ブラウザなし |
| `npm run test:e2e` | 既定の `built`・`debug`・`ui`・`settings` 全project |
| `npm run test:ui` / `npm run test:editor` | 変更箇所の短い確認。全projectの最終チェックは代替しない |
| `npm run test:coverage` | 同じ既定ケースをsourcemap付き解析buildで再実行し、project別のnative V8レポートを生成 |
| `npm run test:long` | 明示実行する長い通常campaign経路と10状態VRT |

本番の通常buildは4173、専用debug buildは4175、一時ソースコピーのfixture／エディターは4174で起動する。エディターの保存テストは本来の標準設定を上書きしない。`built`等のproject名はテストの所属を表し、取得元buildを厳密に限定するものではない。例えば通常配布テストも保存key隔離のためdebug originへ移動し、`settings`には独立buildやHMRもある。

待機は対象の完了条件を再試行付きassertionやイベントで待つ。準備完了と無関係なボタン、固定sleep、操作間のcooldownを同期条件にしない。表示時間はPlaywright Clockで制御し、実ネットワークの保留は解放可能なgateを使う。リサイズは最終ステージ寸法と札／マーカーの位置関係を同時に確認し、途中の寸法を成功にしない。画像不一致をsleep、許容差増加、無審査のbaseline更新で隠さない。

CIを直列実行して5分未満にすることを目指すが、超過だけをPR却下やtimeoutの理由にしない。品質を先に担保し、低コスト層への移動、重複除去、時計制御、明示実行の範囲を検討する。同じ保証で目標へ収まらない場合は、実測と残る保証をIssueへ示し、次の最適化で相談する。必要なテストの削除やassertionの弱化で時間を合わせない。

録画・承認画像とのoverlayは `playwright.evidence.config.ts` 等のレビュー資料であり、品質ケースのskipとして混ぜない。失敗時の画像・trace・JSON、coverageのHTML/LCOVをartifactへ保存する。基準画像の更新は差分理由と実画像をレビューし、自動生成したから正しいとは扱わない。

## Coverageと差分レビュー

Vitest 5の標準 `@vitest/coverage-v8` で `src/**/*.ts` と `scripts/*.{ts,mjs}` をincludeし、未読込ファイルも分母へ含める。`coverage/unit/` を責務に照らして確認する。率を上げるだけのテストは追加しない。

ブラウザはPlaywright native V8とMonocartを使い、自前のsrc TSをsourcemapで正規化する。全srcの未読込も含め、vendor・テスト・CSSを混ぜない。`coverage/browser/{built,debug,ui,settings}/` はprojectごとの実行由来のレポートであり、同じ分母を平均・合算したり、unit率と統合したりしない。解析buildは通常配布と別に生成し、通常buildの短い境界も実行する。

CIはgit上の品質テストファイル、runnerの `--list`、実JSON結果を照合し、空／未発見ファイル、重複名、未実行、skip/todo/only、失敗・retry・期待失敗を拒否する。Vitestの標準Reporter APIで個別retryと期待失敗も確認する。ブラウザ解析は共有fixtureを必須にし、追加context/pageや遷移前回収漏れ、ケースごとの収集欠落を拒否する。手書きの仕様ID・テストID台帳や独自runnerは増やさない。

自動検査は登録漏れや未実行を検出するが、assertionの意味や自然言語仕様の完全性は証明しない。PRでは次を確認する。

- 変更する仕様参照、公開入力、期待結果、具体的なテスト名とassertion、担当する保証責務を示す。
- テストが実際に通す親イベント・保存先・状態遷移を読む。guard／throttleは対象操作と許す通常入力を確認する。
- 修正前や妥当な一時的破壊で回帰テストが失敗することを確認し、復元後結果を記録する。全テストへ機械的な変異試験を足すという意味ではない。
- 既存仕様の不足・未監査・矛盾が判明したら明記する。将来未実装を混ぜず、目視やCI成功で不足を消さない。
- 正確な最終headとbaseの統合commitで全既定project、実行JSON、coverage、VRT差分を確認する。基準画像の承認とテスト成功は別に確認する。

mainの保護・required checksが未設定のため、CIを実装しただけでマージを強制的に止めたとは報告しない。最終チェックと承認は [マージ実施側の確認](testing/review-controls.md) が担う。
