# 文書の書き分け

文書を読む人が、現在有効な仕様と、判断の経緯・作業計画・検証記録を取り違えないようにする。

| 置き場 | 書く内容 |
| --- | --- |
| `specs/` | 現在有効なゲーム・画面の振る舞い、制約、責務、具体例。合意済みの要求を記し、実装状況はIssueで追跡する |
| `docs/adr/` | 後から理由を参照する必要がある判断の背景、選択肢、決定、結果。決定ごとに1ファイルを置く |
| `docs/milestones.md` | 実装順、依存関係、到達点。進捗はIssueで追跡する |
| `docs/design-guidelines.md` | UIの見た目と操作状態の設計指針。実装仕様・必須テスト・マージ条件とは区別する |
| `docs/testing.md` | テストの方針、環境、実行方法の分担 |
| `README.md` | 文書の入口、環境構築、実行方法、ソース構成 |
| Issue | 変更単位、作業内容、受入条件、進捗 |
| `art-src/README.md` | 素材の出典、加工、利用条件 |

## 仕様を書くとき

- 「今どの入力で何が起きるか」「何を表示するか」「どの境界が責任を持つか」を現在形で書く。現時点で決まっていない値や機能を、決定済みの仕様のように書かない。
- 実装したIssue、採用日、誰が調整したか、以前の値、検証時の成功件数、変更理由などの経緯を入れない。仕様の根拠を残す必要があればADRを作り、仕様は現在の結論だけを記す。
- 将来の着手順、保留中のタスク、Issueの完了判定は計画またはIssueへ書く。現在の仕様が扱わない範囲は、必要な場合に限り「対象外」として書ける。
- 値の正本が設定ファイルにあるときはそれを参照する。値を仕様にも載せるなら変更時に両方を更新する。古いスクリーンショットや検証結果を現在の表示例として残さない。
- 仕様・実装・公開の振る舞いを検証するテストを同じ変更で整合させる。履歴を残すために古い仕様文を併記しない。過去の版はGit履歴で確認する。

## ADRを書くとき

判断の理由が後の変更時にも必要なら、`docs/adr/`に連番のMarkdownを追加する。タイトルと日付に加え、**背景・判断・結果**を簡潔に書く。検討した別案があれば、その不採用理由も書く。関連する仕様やIssueへリンクしてよいが、現在の仕様値や受入条件の正本にはしない。判断を変更したときは古いADRを書き換えず、新しいADRで置き換えを示し、仕様を現在の結論へ更新する。

作業の成否や実行ログだけならADRにしない。必要な証跡はIssue、テスト結果、コミットに残す。
