# 文書の責務と更新

利用者が現在の仕様、共通判断、画面の値、制作手順、検証結果を取り違えないようにする。

| 正本 | 答える問い |
| --- | --- |
| `specs/` | ゲームで何が起きるか。入力・結果・制約・責務の現在の契約 |
| [デザインシステム](design-guidelines.md) | 何を優先し、どの基盤・部品・状態・patternをどう使うか |
| [画面設計](ui-screen-design.md) | 目的・情報・操作・全パーツ・構図をどう定めるか。画面仕様への入口 |
| `docs/ui-screens/` | 対象画面の部品割当、素材、具体値、配置、状態、操作結果と適用理由 |
| [制作手順](ui-asset-production.md) | 原画像・Figmaをどう制作・実装・比較し、誰が何を確認するか |
| [UI実装対応](ui-adoption.md) | 画面仕様からどのコードを読むか |
| [テスト設計](testing.md) | 何をどの層・条件・commandで検証するか |
| `docs/adr/` | 継続して参照する判断の背景・選択肢・決定・結果 |
| [段階別計画](milestones.md) | 実装順と依存関係。現在の進捗はIssue |
| `README.md`、`AGENTS.md` | 入口・実行方法、必要なときに読む文書への案内 |
| Issue・PR | 対象課題、受入条件、判断と根拠、進捗、対象revisionの検証・レビュー |
| `art-src/README.md` | 素材の出典、加工、利用条件 |

共通ルールへ画面固有値や採用会話を置かず、画面仕様へ共通ルールを複製しない。制作手順やPRチェック欄へ別の寸法・レビュー規則を作らない。実装値の正本がCSSや設定にある場合はリンクし、説明に値を併記する範囲だけ同時更新する。

## 保存先と共有

明示された保存先を優先する。継続的な設計・仕様・制作手順はrepo、開発の判断・進捗はIssue、画像・ファイル・保存して読む長い資料はSpace、短い報告は会話で扱う。同じ本文を複数の正本に分断しない。

レビュー資料は対象版の成果と必要な比較だけを表示する。原画像と必要な過去版を保持しつつ、途中経過・古い案・作業履歴をレビュー本文へ積み上げない。Spaceへ保存する場合は正式なPage／reference経路を使い、読戻しと必要な表示・受取側のアクセスを確認する。

保存方針は投稿・公開権限を広げない。非公開会話・個人情報・内部対応表・非公開Pageリンクを公開文書やPRへ含めない。原指示への対応は非公開の確認資料で扱い、公開出典は公開一次資料に限定する。素材の利用条件と公開範囲は別に確認する。

## 更新の単位

仕様は現在形で、どの状態の入力が何を変えるかを記す。未決値、表示案、実装済み、本人の承認を区別する。採用日、会話番号、以前の値、成功件数、担当者の作業履歴を現在の仕様へ残さない。必要な履歴はGit、判断理由はADR、検証結果は対象Issue／PR等で扱う。

ADRは一つの継続的判断につき一ファイルとし、背景・判断・結果を書く。変更する場合は新しいADRから置換を示し、旧ADRの判断本文を現在の規則として書き換えない。単なる作業ログはADRにしない。

文書再編では、原要求と必要な役割から構成を決める。旧文書は欠陥と参照の検出に使い、規則の正しさを保証する資料にしない。本文を書いた後、原要求と照合して欠落・逆転・過剰一般化・個別例への狭め過ぎを確認する。

## 変更時の確認

変更した正本から、AGENTS、README、PRテンプレート、関連specs・ADR・画面仕様・適用一覧の導線を確認する。ローカルのリンク・見出し、仕様との責務、古い規則への参照、重複を検証する。廃止する見出しへの参照は現行の意味に対応する入口へ更新する。

検証は[文書のみの確認](testing.md#外観と提出前検証)に従い、製品source・素材・golden・試験設定が変わらないことを差分で確かめる。文書整備のためにゲームsuiteを再実行せず、製品変更がある場合は必要な保証を省かない。
