# UI設計から画像制作・承認・実装へ進む手順

本書はUI制作の進行と採否の正本である。画面の目的・情報・操作は[画面設計](ui-screen-design.md)、UIの表現は[デザインガイドライン](design-guidelines.md)、ゲームの振る舞いは[仕様概要](../specs/overview.md)と各詳細仕様、検証の担当層とコマンドは[テスト設計](testing.md)を参照する。本書を背景・キャラクターの見た目の説明書として使わない。

ゲーム仕様を保つことと、仮UIのボタン・配置・背景・立ち絵を保つことは別である。新しい画面案は目的と操作結果から組み直す。既存CSS・画面・生成案を自動的な見本や制約にせず、対象の完成画像が承認された後はその承認範囲を守る。

## UI開発の必須ゲート

下表の前提が未達なら、依存する工程へ進めない。文書だけの変更には画像生成・完成画像承認・製品撮影を要求しない。文書の変更を製品UIの変更・承認・検証完了として報告しない。

| 工程 | 次へ進むための成果 | 未達時の扱い |
| --- | --- | --- |
| 1. 画面設計 | 対象画面・状態・対象外、必要情報、全操作の結果・確定点・戻り先・影響を仕様に対応付けた設計 | 背景制作で設計の不足を埋めない |
| 2. 資料確認 | 場所設定の決定、参照原画像の取得と担当者の実見、参考UIの操作構造の調査 | 未確定の場所はユーザーへ確認。画像未取得は取得待ち、挙動未確認は未確認として残す |
| 3. 制作と保存 | 生成への実画像入力、設計を満たす完成画面案、原出力・入力資料・版を辿れる保存先 | 未添付・未保存・背景だけの成果を完成画面に数えない |
| 4. 完成画像承認 | ユーザーの明示承認と、固定版・対象画面／状態／寸法・比較条件の組 | 参照採用、生成成功、背景承認、旧案、実装済みを実装承認へ読み替えない |
| 5. 製品実装 | 承認範囲を本番UI・実データ・意味入力へ接続 | 未承認の追加・削除・配置変更が必要なら設計と画像へ戻って再承認 |
| 6. 外観と操作の検証 | 同条件の実画面・直接画像比較と、仕様の操作／状態保証の結果 | 画像承認、pixel差分、操作テスト、VRTの成功を互いの代用にしない |
| 7. PR審査 | exact base/head、設計・承認・画像・検証への閲覧可能なリンク、未確認事項 | 意味ある未合意差・根拠不足をreject。CI成功・チェック欄だけで解除しない |

## 画面設計と資料確認

[画面設計の記入項目](ui-screen-design.md#画面ごとに決めること)を先に埋める。静的なホーム・街の場所選択、動的なADV会話、ショップ等の子画面は別の対象として、入口と出口を対応付ける。場所選択から会話へ接続することは、会話画面の新しい意匠まで制作する許可ではない。

現在のゲーム仕様、本編用の仮コンテンツ、既存実装の便宜、今回の決定、未決事項を区別する。場所の設定・用途が未確定なら、決めるべき点をユーザーへ確認する。「雰囲気が合いそう」で建物・NPC・店・イベントを捏造し、画像制作へ進めない。参考作品のルールを本作へ輸入しない。

参考ゲームは実画像・動画を開き、場所の識別、選択／実行、押下後の遷移、戻る、情報の優先度、選択・focus・使用不可の区別を調べる。資料URL・動画名・時刻と、実際に見えた操作構造、本作へ採る理由、映像だけでは分からない点を残す。静止画やPVに映らないクリック結果・キー操作・時間消費は推測せず未確認とする。装飾の模倣だけで調査済みとしない。

## 原画像を文章へ置き換えない

背景・キャラクターなどの見た目を言語化して渡すことを禁止する。原画像の形容詞、要約、視覚説明を依頼文・引継ぎ・プロンプトへ書き、原画像を代用または補完してはならない。原画像と一緒であっても見た目の説明を追加しない。

文字で伝えてよいのは、資料名・画像の役割・対象画面、場所設定としての決定、UIの必要情報・配置・寸法・操作仕様、生成の用途・透過・出力条件である。背景や人物は原画像そのものを渡し、担当者が開いて確認し、生成時にも実画像を入力として添付する。リンク、ファイル名、文章、別担当者の「見た」は画像入力・担当者の実見の代わりにならない。

| 確認 | 残す証拠 | それだけでは証明しないこと |
| --- | --- | --- |
| 原画像の入手 | 正規取得元、固定reference／file ID、版・SHA-256・実寸、取得成功 | 担当者が見たこと |
| 担当者の実見 | 実際に開いた画像の識別子と閲覧結果。破損・別資料なら差し戻す | 生成へ添付したこと |
| 生成の実入力 | 実行した生成依頼と添付画像識別子の対応、生成結果との対応 | URLを書いただけでは添付を証明しない |
| 成果の保存 | 原出力と完成画面の固定版、保存先・hash・寸法、読戻し | 保存だけでは承認を証明しない |
| 完成画像の承認 | 対象固定版とユーザーの承認元・範囲 | 製品へ接続したこと |
| 製品の確認 | 実装commit、撮影・pixel比較・操作検証 | 参照画像や生成結果では代替できない |

画像が未取得・閲覧不可・生成入力へ添付できないときは、対象画像と止まる工程を報告し、画像の入手・アクセス・再添付を求める。依存しない仕様読解・UI設計は進めてよい。画像の欠落を文章で埋めたり、親のローカルパスが別環境にもあると推測したりしない。Space Pageでは本文をread_page、画像をread_page_referenceで開く。本文の説明を画像扱いしない。

## 制作依頼と保存

生成前の依頼は「対象画面／状態／目的／必要情報／各操作／対象外／添付画像の役割／出力条件／保存先」を一組にする。既存ボタンや立ち絵を残す指定は、今回の設計または対象承認に根拠があるときだけ行う。背景差替えだけで必要情報・導線・確定点が未設計の案は棄却する。

完成画面案はプレイヤーが見る情報と操作状態を含む。制作物には次の役割を付け、同じ画像の承認を別用途へ拡張しない。

| 役割 | 用途 |
| --- | --- |
| 参照原画像 | 制作担当者と生成への入力。製品素材の利用許可を意味しない |
| UI研究資料 | 参考ゲームの情報・操作構造を調べる入力 |
| 完成画面案 | 情報・配置・状態を含む承認対象。製品スクリーンショットではない |
| 背景・人物・部品素材 | 製品に接続する個別素材。単品の採用は完成画面の承認ではない |
| 製品スクリーンショット | 本番UIの実描画。自己承認用の完成画面案に読み替えない |

製品の文字・数値・状態・操作と単純な枠はHTML/CSS/SVGで管理する。完成画面案を一枚貼りして製品UIにしない。UIの図案・質感が必要なら、先に決めた情報・操作構造のために制作する。素材未提供の人物は名前と必要情報を残し、別人の画像で代用しない。背景取得失敗でも操作と判断情報を読める表示を保つ。

repo内文書の正本はrepoで更新する。新しい報告・参照・画像成果の保存先はユーザー指定のSpaceとし、公式Page/reference経路で保存・読戻しする。既存のLibrary記録は過去成果の所在であり、新規保存の行き先にしない。公開repoへの画像保存が必要なら、公開対象・個人識別表示・利用条件を確認し、その公開の許可範囲を守る。非公開の原画像をPR・公開artifactへ転載しない。

原出力を保持し、派生素材には入力、加工内容、hash、実寸を対応付ける。切抜き・補正・拡大・形式変換を無加工と呼ばない。無劣化変換は復号画素の一致を確認し、単なる拡大表示を高解像度化と呼ばない。製品採用素材の出典・加工・利用条件は[素材メモ](../art-src/README.md)へ記録する。生成成功を権利・利用条件確認の代用にしない。

## 完成画像承認と変更管理

固定版ごとに次を対象Issueまたは承認資料から辿れるようにする。

- 画像referenceまたはパス、version・SHA-256・実寸。
- ユーザーの承認元メッセージへのリンクまたは会話／メッセージ識別子、承認日時、画面・状態・寸法の範囲。
- 対応する画面設計と仕様、比較fixtureの固定版・起動方法。人物と枠順、HP・症状・時刻・文言・選択・scroll・操作状態を再現できる条件。
- 動的領域や資料注記等の差を認める場合、その領域・理由・事前承認元。指定がなければ許可領域は空。

通常・選択・詳細・hover・pressed・focus・disabled・狭幅等から、今回変わる見た目と挙動を具体的に示す。対象を省略する場合も範囲を承認記録で特定する。全画面にHPや立ち絵を機械的に追加せず、その画面の判断に必要な情報を含める。通常画面の承認を別状態・別寸法へ自動拡張しない。

承認後に不足情報・追加操作・配置・読みやすさの問題が判明したら、該当UIの実装を止め、設計と完成画像を改訂して再承認する。旧版は保持する。既存CSSや共通トークンへの統一、余白を埋める都合で承認範囲を変更しない。現在の実画面、過去のマージ、共通部品の適用記録で自己承認しない。

## 実装後の直接比較と操作検証

承認済みfixtureを本番UIへ接続し、同じ解像度で実撮影する。viewport・DPR・ブラウザ／環境・フォント・素材・表示データ・選択・scroll・描画時刻を揃え、画像decode・自然寸法・実使用フォントを確認する。異なる解像度の画像を伸縮し、位置合わせ・切抜き・ぼかし・色補正で差を隠さない。対応条件で撮影できなければ未達とする。

| 画像証跡 | 必須内容 |
| --- | --- |
| 比較元と実画面 | 固定版承認画像、未加工の製品スクリーンショット、実装commitと撮影条件 |
| overlayと全体diff | 同座標50%overlay、マスクなし・閾値0の全画素diff、非一致画素数／割合、コマンド・ツール版。強調画像には変換方法も記録 |
| 許可領域と診断 | 事前承認領域の可視画像・座標／mask・理由・承認元（なければ空）、領域内とその他UI領域のdiff・別集計。全体diffも保持 |
| 実画像レビュー | 画像一式を直接開いた結果、差の原因・採否、修正後の再撮影／再比較、未解消差 |

データ条件の違いはfixtureを揃えて解消し、意図的なデザイン変更は完成画像の再承認で扱う。maskの後付け・拡張で隠さない。pixel差分は意図しない差を見つける手段であり、差分ゼロや割合だけを合否条件にしない。意味ある構図・配置・情報・状態・素材の差と、説明できるラスタ・素材由来の微差を実画像で区別する。全画面共通フォントの後続課題を扱う際も、読めない崩れや大きな位置差を微差扱いしない。

操作と状態は[テスト設計](testing.md)の層で検証する。各操作について遷移・戻る・確定／取消・入力可否・focus復元と、時間・HP・所持・フラグ・乱数への変更／非変更を仕様へ対応付ける。有効な再訪・押し直しは受理し、現在状態で無効になった確定だけを拒否する。画像・撮影・CI件数で操作保証を代替しない。既存goldenのVRT成功もユーザーの完成画像承認とは別である。

## PRでの採否

[PRテンプレート](../.github/pull_request_template.md)から設計・入力画像の確認・承認・製品比較・操作検証を辿れるようにする。非公開画像は権限のあるSpace参照を使い、閲覧できない担当者にはアクセス不足を解消してからレビューを依頼する。公開してアクセス不足を解消しない。

「背景替え＋既存UI踏襲」「別対象の会話画面を追加」「原画像を文章へ置換」は、[棄却例](ui-screen-design.md#今回の失敗案を判定する例)のように前工程で止める。未説明・未合意の意味ある差、設計・原画像入力・承認・比較証跡の欠落が残るUI変更はrejectする。微差の存在だけではrejectしない。

実装と必要な全ローカル検証を終えてから公開し、完成PRを独立レビューへ渡す。未完成差分をCIで試すpushは行わない。提出形式とmerge権限は現在のユーザー指示に従い、完成draft PRでも製品承認やmerge権限が得られたとは扱わない。
