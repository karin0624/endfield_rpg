# デザインから制作・実装・検証へ

対象と固定版を保ち、設計、画像制作、実装、一致検証、本人の判断をつなぐ。本作では本人がFigmaでデザインを作成し、dotが実装を担当する。[デザインシステム](design-guidelines.md)は共通判断、[画面設計](ui-screen-design.md)は画面の情報・操作、[テスト設計](testing.md)は検証層とコマンドの正本とする。

## 責務

| 担当 | 責務 |
| --- | --- |
| 本人・デザイン担当 | Figmaで構図・部品・状態を設計し、変更範囲と保持条件を指定する。意匠の変更を判断する |
| 素材制作担当 | 本人の有効な制作指示から対象素材を作る。参照画像付き制作・編集では原画像も実入力に使い、原出力と派生物を対応付ける |
| 実装担当 | 固定版Figma・実画像・操作仕様を読み、既存構造へ接続する。不足は具体化し、意匠や機能を無断で補わない |
| 視覚レビュー担当 | 履歴を継承しない独立したcontextで、必要な実画像と仕様を直接確認し、見える問題と影響を返す |
| 進行担当 | 要求・固定版・工程の実施証拠を照合し、不足の修正と再確認を進める。本人判断を検査成功で代替しない |

視覚レビューは余白、まとまり、釣合い、階層、可読性、図案の識別性を扱う。CSS値・DOM寸法・設計との一致検査、制作順序の監査とは分ける。「装飾として成立する」「破綻がない」だけで合格にせず、用途に対する仕上がりの具体的な弱さを確認する。レビュー担当は版・状態・箇所・見える問題・視覚的影響と根拠を示し、修正方法、寸法、variantや再比較計画は設計側が決める。指摘を機械的に全て直さず、本人の指示・目的・実画像・利点と弊害に照らして採否を判断する。

## 適用条件

| 作業 | 必要な制作・確認 |
| --- | --- |
| 新しい画面・構造 | 目的、全パーツ、一般DS調査、共通契約、画面への割当、Figmaと状態画像を先に確定 |
| 参照画像のない新規制作 | 本人が指定した内容・用途・出力条件を保持して制作し、生成画像を要求へ照合する。原画像の入手・実入力は対象外 |
| 参照画像付き制作・画像編集 | 参照・編集元の原画像の入手・実見・実入力、本人の制作・変更指示と保持条件、原出力・派生物、実画像比較 |
| 既存素材の利用 | 固定版・出典・利用条件・実見。生成しなければ生成入力の証拠は不要 |
| Figmaに合わせる実装修正 | 固定版と差を確認。同条件の実撮影・一致検証と影響する操作保証。位置合わせのために新規生成や無関係な参考研究を増やさない |
| 文書のみ | 要求との対応、仕様・導線・見出し・リンク・差分を確認。製品を変えなければゲームsuite、画像生成、撮影は不要 |

複数を含む場合は対象ごとに適用する。対象外は理由を示し、製品変更を文書のみへ分類しない。同じ対象・版・条件の既存証拠は再利用できる。

## UI開発の必須ゲート

| 段階 | 成果と次へ進む条件 |
| --- | --- |
| 設計 | 画面の目的、必要情報、全操作の結果、全パーツと共通契約の割当。未決の設定・入力・状態を解消 |
| デザインの固定 | 対象Figmaのfile／node／版と実画像、画面・状態・寸法、変更と保持の範囲を特定 |
| 素材制作・確認 | 必要な場合のみ実施。参照なしの新規制作は本人の指定、参照画像付き制作・編集は原画像と指定を入力にする。生成画像を要求へ照合し、比較元がある場合は局所・全体も直接比較して未達を修正 |
| 実装開始 | 本人の対象デザインと実装指示が揃う。表示案・背景単品・旧版を別画面や全状態の承認へ拡張しない |
| 製品検証 | 同条件の実画面、一致検証、影響する操作・状態の保証。意味ある未合意差を残さない |
| 提出・レビュー | 実装と必要なローカル確認が完了した通常PRを作り、完成headを独立レビュー。本人の必要な制作手順レビューも完了してから、現在の権限でマージ |

文書の存在やチェック欄だけで通過を判定しない。前提が欠ける対象だけ止め、独立して進められる作業は続ける。既に対象デザインと実装指示がある場合へ同じ承認を追加要求しない。

## 原画像を文章へ置き換えない

原画・参照画像のない新規制作では、本人が指定した内容・用途・出力条件を保持して生成する。原画像を必須条件にせず、不要な原画提出を求めない。制作後にその画像を編集する場合は、生成画像そのものを編集元として渡す。使うべき参照画像があるのに未取得である場合を、参照なしの新規制作へ分類しない。

背景・人物・図案等の参照画像付き制作・画像編集では、原画像そのものを保持し、担当者が実際に開き、生成・編集へ正式な画像入力として渡す。リンク、ファイル名、別担当者の閲覧、文章要約だけでは実入力にならない。参考UIも形・配置・図案と文字の関係を採るなら原画像・動画の実フレームを渡す。

本人が新規に作る内容、指定した変更内容、変更してよい範囲、保持条件は、その意味と範囲を維持して制作へ渡す。形・比率・輪郭・陰影・材質・光沢・色・鮮明さ・構図等の明示指示を、原画像の文章代用禁止を理由に削除・禁止しない。一方、担当者が参照画像の見た目を独自に言語化し、代用・補完することは避ける。原画像の実利用と本人の制作指示は両立させる。

資料名、参照する役割、UIの構造・文言・操作・配置、透過等の出力条件は識別可能に記す。本人が共通の画風目標や段階を求めた場合も指定を保持し、基準画像を使う制作では毎回その画像を実入力する。promptの記述を正式APIの制御値や再現保証と称さない。

原出力保存、完成画像の採用、製品確認はそれぞれ証拠で確認する。原画像の入手・実見・実入力の確認は参照画像付き制作・編集へ適用する。必要な参照画像が取得不能なら対象画像と止まる工程を特定し、正規取得・アクセス確認を行う。文章や別人の画像で欠落を埋めない。別環境のlocal pathが使えると推測しない。

## 素材の変更と比較

1. 本人の制作要件を確認し、参照画像や共通の画像基準がある場合はその固定版を特定する。今回候補、保持する旧版、変更箇所を識別し、原依頼と全ての有効な改訂を照合する。
2. 本人の指定から期待する結果と確認方法を決める。参考作品や共通画風への適合を扱う場合は実画像、一般指針、類似例を調べ、現状の不足、改善する要因、反証条件へ対応付ける。例示された対象だけへ要求を狭めない。
3. 本人の指示に沿って制作する。簡略化を物体削除へ、追加を別物へ、限定修正を無関係な変更へ読み替えない。参照画像・編集元がある場合は変更せず保持し、許可されたcrop・補正等の派生物に入力・加工範囲・hash・寸法を対応付ける。加工を無加工と呼ばない。
4. 生成とは別の比較contextへ候補の実画像と本人の制作要件を渡す。画像基準がある場合はその実画像も渡し、形・比率・輪郭・陰影・材質・光沢・色・鮮明さ・構図のうち要求に関係する観点で、変更箇所と保持箇所を比べる。参照なしの新規制作は要求への適合を確認し、存在しない原画との一致を検証条件にしない。
5. 具体的な不一致を、有効な制作指示の範囲で限定修正へ戻す。修正には編集元画像を実入力し、修正後の実画像を同じ要件と、画像基準がある場合はその基準へ戻して、改善と意図しない変更を再確認する。

細部の密度を合わせる要求は、原参考と候補の対応領域を並べて比較する。遠近はcameraからの距離、配置、遮蔽等から判断し、表示pixel寸法と混同しない。遠景だけの参考で近景の一致を証明しない。必要な対応参考が無ければ取得・確認へ進め、未確認範囲を残す。似た物・同程度の距離と用途を対応付け、画風とデフォルメを比較する。例示された一つの物体だけを直す規則にせず、全場面へ同じ判断軸を適用する。共通の指示を送った事実と、結果が統一されたことを区別する。

## 実画像の視覚レビュー

完成部品単位の切出し・拡大表示を先に一つずつ開き、その後に元の全体画像で構図・主要領域・部品間の関係を確認する。全パーツと必要状態を、それらを含む完成部品の表示へ対応付ける。文字・線ごとの機械的な分割や全pairの切出しは不要。

切出しには元版、対象・状態、実寸、元座標、表示倍率を付ける。内部・外周・focusと、隣接部品や背景との関係が分かる周辺を含める。間の空間や比較する双方が欠ける場合は作り直す。細部が読めなければ追加表示を用意し、拡大と実表示の識別性を区別する。

文字の字面、図案、枠、可視の余白、整列、釣合い、階層、背景との関係を実画像で判断する。適用値が揃う、clipがない、テストが通るという理由だけで美観を合格にしない。局所の確認後、関連画像・画面間も比較する。一部の成功を未確認の部品・状態・領域へ広げない。

通常・focus・selected・disabled等と、長文・折返し・文字拡大・小画面・最大桁のうち対象が対応する境界条件を確認する。問題が見えた箇所だけを初めから選ぶ方法で全件確認を代替しない。

## Figmaからの実装と直接比較

実装担当は固定版Figmaと画像を開き、対象画面、全パーツ、状態、素材、文字、寸法、配置、余白を確認する。ツール出力の参考コードをゲーム仕様の正本にしない。ゲーム状態・意味入力・確定処理は既存の[責務境界](../specs/overview.md#責務境界)へ接続する。文字・数値・状態・操作は実UIとして保持し、完成画面を一枚貼りして代替しない。

同じviewport、DPR、ブラウザ／描画環境、実使用font、素材decode、画面state、data、scroll、animation時刻で製品を撮影する。比較条件に違いがあれば記録し、その条件での一致を未確認とする。

| 証拠 | 内容 |
| --- | --- |
| 比較元と製品 | 固定版の原画像、未加工screenshot、対象commit、撮影条件 |
| 差分 | 同座標50%overlay、無マスク・閾値0の全体diff、非一致画素数／割合、使用commandとtool版 |
| 診断領域 | 事前に認められた領域・理由と範囲。無ければ空。領域別診断を使っても全体diffを保持 |
| 結果 | 実画像の直接確認、原因、修正と再撮影、残る差と未確認点 |

本作の実装は、テキスト・アイコンの僅かな描画差を除いてpx単位で一致することを目標とする。無関係な領域の位置・形・色・余白の差を微差へ含めない。文字やアイコンなら自動的に許容するのではなく、該当箇所を拡大し、条件差やラスタ差として説明できるか確かめる。説明できない差は修正または本人の判断へ戻す。

伸縮、位置合わせ、ぼかし、色補正、事後のmask拡張で不一致を隠さない。意図した変更、描画条件差、未承認の変更、実装不一致を区別し、実装不一致は同条件で修正・再比較する。

## 制作完了・採用・テストを区別する

prompt、版番号、保存成功、担当の完了宣言は実際の結果の代わりにならない。独立レビューへは共通DS・対象仕様・対象にある原参考・固定成果を渡し、制作会話、過去の診断、期待する答えを継承させない。画像から制作順序を推定せず、工程の確認は進行担当が実記録で行う。これらの手順の文書化を、新しいデザイン制作やレビュー自動化を開始する指示として扱わない。

進行担当も原要求と全有効改訂、実際の制作指示、対象にある原画像、候補を照合し、未達を修正してから本人の採用判断へ出す。未完了を承認待ちへ置き換えない。比較画像を作ったことや開いたことだけで、要求された美術的な成功を主張しない。

視覚レビューは見た目の品質、一致検証は固定版の再現、操作テストは仕様上の入力と結果、VRTは既存baselineとの回帰を扱う。どれか一つの成功を他の成功へ読み替えない。通常画像の採用を別画面・別寸法・全状態へ拡張しない。意匠の変更が必要なら本人のFigmaと対象仕様を更新し、対象範囲の判断後に実装する。

## 制作依頼と保存

依頼では対象、目的、参照画像の有無と存在する画像の役割、制作・変更指示、保持条件、対象外、出力条件、保存先を一組にする。参照原画像、研究資料、素材、完成画面、製品screenshotの役割を区別する。素材の採用と完成画面の採用は別である。

正本と共有は[文書の書き分け](documentation.md#保存先と共有)に従う。原出力と必要な履歴を保持し、レビュー面には現行候補と判断に必要な比較だけを置く。途中の操作履歴や旧案を積み上げない。非公開会話・原画像・内部資料を公開PRや公開文書へ転記しない。公開出典は公開一次資料に限定する。

## PRでの確認

[PRテンプレート](../.github/pull_request_template.md)から適用工程と証拠を辿れるようにする。全必要ローカル検証後に公開し、未完成の検証をCIへ委ねない。文書のみの場合はリンク・見出し・仕様・差分を検証し、未実行の製品試験を成功と報告しない。完成PRの独立レビュー、本人の必要なレビュー、最終headのCIを別々に確認し、現在のマージ権限に従う。
