# UIの承認・実装と画像制作の手順

UIの新規作成・変更は、以下の順で進める。pixel diffは意図しない差を発見するために用い、完全画素一致や差分ゼロをマージ条件にしない。合意した構成・位置・情報・枠・質感を変える意味のある差と、フォントのラスタ差・既存立ち絵素材の微差を区別する。フォントは全画面共通の書体・太さ・サイズとして揃え、1画面だけの完全一致へ追い込まない。AI生成画像を使わないHTML/CSS/SVGの変更にも適用する。[UIデザインガイドライン](../specs/design-guidelines.md)は共通ルールであり、承認画像と異なる構図・寸法・書体・材質へ作り替える根拠にはしない。

## UI開発の必須ゲート

### 1. 必要情報を含む完成画像を承認する

実装前に、必要なHP・状態・人物数・名前・操作・エラーや制約を反映した完成画像を提示し、対象画面と状態ごとにユーザーの明示承認を得る。通常・選択・詳細・hover・pressed・focus・disabledなど、変更対象に含まれる状態と画面寸法を揃える。対象を省略するときも、その範囲を承認記録で特定する。雰囲気や背景だけを了承された概念図、必要情報が欠けた画像は、完成画面の実装承認に置き換えない。

承認記録は、既存の対象画像のREADMEと対象Issue／PRから辿れるようにする。画像は上書きされない固定版で保存し、次を一組で記録する。

- 画像の固定パスまたはファイルIDとversion、SHA-256、画像の幅・高さ。
- ユーザーの承認元メッセージへのリンクまたは会話・メッセージ識別子、承認日時、承認された画面・状態・寸法の範囲。
- 比較fixtureの固定版・起動方法・入力経路、人物と枠順、HP・症状・時刻・文言・選択対象・スクロール位置・操作状態。承認画像と同じ表示を再現できるデータ条件。
- 動的領域等の差を認める場合は、事前に承認された領域・差の内容・理由・承認元。指定がなければ許可領域は空とする。

### 2. 変更が必要なら画像へ戻り、再承認する

承認後に必要な情報の不足、追加操作、状態、レスポンシブ配置、読みやすさの問題などが判明したら、UI実装を止める。元画像を改訂し、必要な差分を含む完成画像でユーザーの再承認を得てから実装する。旧版を保持し、新版の識別子と承認元を記録する。必要なHPの追加や冗長要素の削除であっても、実装しながら補ってはならない。

構図・枠・余白・位置・サイズ・書体の重量・材質を「実装裁量」「共通トークンへの統一」「空白を埋めるため」として変更しない。ガイドや既存CSSが承認画像と矛盾する場合も画像を勝手に変えず、矛盾を解消する画像・仕様の組を再承認する。現在の実画面を新しい承認画像として自己承認しない。

### 3. 実画面を同じ画素条件で直接比較する

承認済みfixtureを本番UIへ接続し、画像と同じ解像度で実際に撮影する。例えば1672×941の承認画像には1672×941の実画面を使う。viewport、device scale factor、ブラウザ／コンテナの版、フォント、素材、表示データと操作状態を固定し、画像decode・自然寸法・実使用フォントを撮影前に確認する。サイズの異なる画像を引き伸ばして合わせたり、比較を通すために位置合わせ・切抜き・ぼかし・色補正をしてはならない。対応解像度で実撮影できなければゲート未達として報告する。

承認画像と実画面を直接入力にして、以下を画面・状態ごとに保存する。

| 証跡 | 必須内容 |
| --- | --- |
| 原画像・実画面 | 固定版の承認画像、加工していない実スクリーンショット、対応する実装commitと撮影条件 |
| 50%重ね合わせ | 同じ座標で承認画像と実画面を各50%合成した画像 |
| 全体pixel diff | マスクなし・閾値0の全画素差分画像、非一致画素数・割合、比較コマンド・ツールの版。未加工の差分値を保持し、強調表示を併記する場合は変換方法も記録 |
| 許可領域 | 領域を可視化した画像、座標／maskデータ、各領域の差の内容・理由・事前承認元。領域なしの場合も空であることを記録 |
| 領域別の検査 | 許可領域内と、それ以外のUI領域の差分画像・差分画素数・割合。全体diffを残した上で別集計 |
| 画像レビュー | 原画像・実画面・overlay・diffを実際に開いて確認した結果、発見したずれ、修正後の再撮影・再比較結果、未解消差分 |

データ／機能状態が違う画像同士を比較してからmaskで除くのではなく、まず承認済み比較fixtureへ揃える。意図的なデザイン変更は承認画像自体を改訂・再承認する対象であり、除外領域に逃がさない。許可領域は事前承認されたものだけとし、枠・質感・文字・配置のずれを隠すmask、実行後のmask拡張、都合のよい範囲だけの切抜きを禁止する。アンチエイリアス等の差も全体diffから消さず、原因と画素範囲を提示する。各差を「意図しない意味のある差」「説明済みの素材・ラスタ由来の微差」「全画面共通タイポグラフィ等の後続課題」に分類して記録する。フォントや既存立ち絵の微差は完全一致にせず説明付きで残せる。背景も非ゼロという理由だけで停止せず、視線・世界観・構図を変える大差かを実画像で診断する。大きな形・配置差を微差の扱いで通さない。

画像を言語化した説明文同士の比較、寸法表だけの比較、「雰囲気が近い」、コードテスト成功ではこの確認を代替できない。画素差分を手掛かりに実画像を確認し、意図しない意味のあるずれを修正して再撮影する。説明済みの微差までゼロにする反復は求めない。機能・キーボード操作・状態保持のテストは別途必要で、画像一致をそれらの代わりにもしない。

### 4. PRで証跡を照合し、不足はrejectする

[PRチェックリスト](../.github/pull_request_template.md)に承認記録、対象状態一覧、上記の画像一式と検査結果へのリンクを記載する。証跡はcommit固定のリポジトリ内ファイルまたは該当CI artifactに保存し、artifactの期限切れで確認できなくなった場合は再保存してからレビューする。承認画像と実画面の種類を明記し、概念図を実行画面として提示しない。

未説明・未合意の意味あるデザイン差、未承認の状態や寸法、承認元の欠落、画像差分証跡の不足が残るUI変更はrejectし、マージしない。非一致画素の存在や割合だけではrejectしない。CI成功やチェック欄だけで解除しない。修正または画像の再承認を行い、証跡を更新して再レビューする。共通UIの適用済み記録・過去のマージ・スクリーンショットの存在は、現在の完成画像の承認証拠にはならない。

## UI用素材の制作

以下の素材制作も必須ゲートの範囲で行う。

文字・数値・操作状態・単純な枠・寸法はHTML/CSS/SVGで管理し、AI生成は追加の図案や質感に使う。ボタンを文字ごと生成したり、状態ごとに別の形を作り直したりしない。

生成時は、デザインガイドラインと制作対象に近い既存のUI素材をAIに渡し、両方を参照させる。ガイドラインを配色・状態表現などのルール、既存素材を輪郭・線幅・質感・余白の見本として使う。適切な既存素材がない場合は、[実装CSS](../src/web/style.css)と実画面のスクリーンショットを見本にする。

新規の図案は、参考ゲームの該当画面の参照画像とデザインガイドラインを直接入力し、用途と目指す方向を伝える。PC画面での情報の優先順位・配置・余白・選択状態を先に決め、その構成に必要な図案だけを生成する。

採用済み素材の差分は、元の採用素材と差し替え対象の参照画像を直接入力し、変更する領域・要素だけを指定する。表情差分と同様に無関係な意匠を保持し、指示にない文字や装飾を足さない。

依頼では、作る部品の用途、実際の表示サイズ、背景透過の要否、必要な状態差分、既存素材から変更したい点を指定する。共通のデザインルールはガイドラインを参照し、依頼ごとに書き直さない。

承認前の素材制作では既存素材と並べ、色・寸法・透過・余白・質感の統一を確認する。色補正を含む変更は完成画像へ反映して承認を得る。承認後にトークン色へ合わせるための補正を加えず、必要なら画像改訂・再承認へ戻る。状態差分は同じ原画から作り、輪郭や余白を変えない。実表示サイズで見え方を確認してから採用し、出典・利用条件を[素材メモ](../art-src/README.md)に記録する。

実画面へ適用した後、想定する表示サイズと背景で文字・状態が読み取れ、選択・フォーカス・使用不可を識別できることを確認する。OSで動きを減らした場合も、操作対象を判別できる必要がある。これらの確認だけでWCAGの全要件を満たしたとは判断しない。

## 納品と実画面確認

制作開始時に「画面／用途／必要実寸／透過／状態／既存原画／採用先」を整理する。素材の状態は概念図、原画、採用版、未提供を区別する。編成では背景は新生成、人物は既存原画、枠・数値・状態・ボタンはHTML/CSSである。画像未提供の仲間には名前と「画像なし」を表示し、別人の立ち絵で代用しない。

元データのidentity・version・実寸・hashと、採用版への加工を素材メモへ記録する。無劣化形式変換はデコード後の画素一致も確認する。拡大表示と元画像の高解像度化を区別する。概念図は`docs/ui-concepts/`、原画は`art-src/`、配布素材は`public/assets/`に分ける。

承認された採用版は実際の画面へ接続し、まず承認画像と同一解像度で上記の直接比較を行う。1920×1080等の追加の表示条件でも人物・床の比率、文字との衝突、トリミング、画質、通常／選択／非活性／focus／詳細復帰を確認する。背景や人物の取得失敗でも暗い下地・名前・判断情報を残す。狭幅・長文・多数候補・reduced-motionの確認を加え、画面記録とテスト結果はPRへ添える。未確認の素材・適用していない画面は[適用一覧](ui-adoption.md)へ明記する。
