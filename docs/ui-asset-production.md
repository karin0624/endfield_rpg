# デザインから制作・実装・検証へ

ユーザーがFigmaでデザインし、実装担当が固定版と操作仕様を製品へ反映する。共通規則は[デザインシステム](design-guidelines.md)、画面への割当は[画面設計](ui-screen-design.md)、検証層とPR手順は[テスト設計](testing.md)を参照する。

## 責務

| 担当 | 責務 |
| --- | --- |
| デザイン担当 | 構図・部品・状態、変更範囲と保持条件を指定し、意匠を判断する |
| 素材制作担当 | 制作指示と、存在する参照原画像を使い、原出力・派生物を対応付ける |
| 実装担当 | 固定版と操作仕様を既存構造へ接続する。不足する資料・仕様を具体化する |
| 視覚レビュー担当 | 履歴を継承しない独立したcontextで実画像を確認し、版・状態・箇所・見える問題と影響を返す |
| 進行担当 | 要求、制作指示、原画像、候補と工程の実記録を照合し、未達の修正・再確認を進める |

視覚レビューは余白、まとまり、釣合い、階層、可読性、図案の識別性を扱う。修正方法や寸法は設計側が決め、指摘の採否を要求・実画像・利点と弊害から判断する。

## UI開発の必須ゲート

| 段階 | 次へ進む条件 |
| --- | --- |
| 設計 | 目的、必要情報、全操作の結果、全パーツと共通契約の割当が決まり、必要な設定・入力・状態に未決がない |
| デザイン固定 | Figmaのfile／node／版と実画像、対象画面・状態・寸法、変更範囲と保持条件を特定できる |
| 素材制作 | 必要な素材を下記手順で制作・比較し、要求との不一致を修正した |
| 実装開始 | ユーザーの対象デザインと実装指示が揃っている |
| 製品検証 | 同条件の実画面で一致を確認し、影響する操作・状態を検証した。意味のある未合意差がない |
| 提出・レビュー | [必要な全ローカル検証と完成PRの独立レビュー](testing.md#外観と提出前検証)、ユーザーに必要な制作手順レビューが完了した |

素材を生成しない作業では生成工程は不要。固定版への位置合わせには、その版と差分を使う。文書だけの変更は要求・仕様・導線・リンク・差分を確認し、製品を変えなければゲームsuite・生成・撮影は不要。

不足する前提に依存する対象だけ止め、独立した作業は続ける。既に対象デザインと実装指示があれば、同じ承認を求め直さない。背景単品や一状態の承認を別画面・全状態へ広げない。

## 原画像を文章へ置き換えない

参照画像のない新規制作は、指定された内容・用途・出力条件から行う。参照画像付き制作・画像編集では、担当者が原画像を開き、生成・編集へ正式な画像入力として渡す。生成後の編集には、その生成画像を渡す。

原画像とともに、ユーザーの制作・変更指示と保持条件を渡す。形・比率・陰影・材質等の明示指示も保持する。担当者による見た目の要約で原画像を置き換えない。

制作依頼には対象、目的、原画像の有無と役割、制作指示、保持条件、対象外、透過等の出力条件、保存先を記す。共通の画風・段階の指定があれば維持し、基準画像を使う制作では毎回その画像を実入力する。

原画像の実入力は、リンク・ファイル名・別担当の閲覧では代替できない。必要画像が取得不能なら対象と止まる工程を示し、正規の取得・アクセス確認を行う。別環境のlocal pathは受取側で使えることを確認する。

## 素材の変更と比較

1. 原要求と有効な改訂から、期待する結果・変更箇所・保持箇所・確認方法を定める。比較元があれば固定版の実画像を開く。
2. 指示に沿って制作する。原出力を保持し、crop・補正等の派生物には入力・加工範囲・hash・寸法を対応付ける。
3. 制作とは別の比較contextへ、候補の実画像、制作要件、存在する基準画像を渡す。要求に関係する形・比率・輪郭・陰影・材質・光沢・色・鮮明さ・構図を局所と全体で確認する。
4. 不一致を制作指示の範囲で修正し、同じ要件と基準で改善・意図しない変更を再確認する。

細部密度・遠近・画風は、用途と距離が対応する領域で比較する。遠近は配置・遮蔽・カメラ距離から判断し、表示pixel寸法と混同しない。要求は例示された一物体に狭めず、対象範囲全体へ適用する。

## 実画像の視覚レビュー

完成部品の切出し・拡大を一つずつ確認し、その後に元の全体画像で構図・主要領域・部品間の関係を見る。全パーツと必要状態を、それらを含む完成部品へ対応付ける。

切出しには元版・対象・状態・実寸・元座標・表示倍率を付け、外周・focus・隣接部品・背景との関係が分かる周辺を含める。拡大時の細部と実表示の識別性をそれぞれ確認する。

文字の字面、図案、枠、可視余白、整列、釣合い、階層を確認する。対象が対応する通常・focus・selected・disabled、長文・折返し・文字拡大・小画面・最大桁も含め、関連する画面間を比較する。

## Figmaからの実装と直接比較

実装担当は固定版と画像から、全パーツ、状態、素材、文字、寸法・配置・余白を確認する。文字・数値・状態・操作を実UIとして作り、ゲーム処理は[既存の責務境界](../specs/overview.md#責務境界)へ接続する。

通常プレイのデザインマスターは[endfield-rpg.fig](../art-src/openpencil/endfield-rpg.fig)。色変数・文字スタイル・共通記号、機能領域で共有する部品、画面専用の部品を再利用範囲で分ける。画面専用の定義は画面フレームの外の`Local Components`区画に置き、画面内にはインスタンスを配置する。ホーム・街・地図以外の既存の独自意匠は`DS未対応`の置き場と名前で識別し、共通デザインへ適合済みとして扱わない。ページ構成と編集後の比較方法は[OpenPencilの手順](../README.md#openpencilでデザインマスターを編集する)を参照する。部品とプロパティは実装の責務・名前へ対応付け、内容差はテキスト／インスタンス交換、同じ部品の状態差は[Variants](https://help.figma.com/hc/en-us/articles/360056440594-Create-and-use-variants)、独立した表示の切替はBooleanで表す。配置と内容に応じた伸縮には[Auto layout](https://help.figma.com/hc/en-us/articles/360040451373-Guide-to-auto-layout-in-Figma)を使う。原画像以外の部品を画像に置換しない。

撮影はviewport、DPR、ブラウザ・描画環境、font、素材decode、画面状態・データ、scroll、animation時刻を揃える。条件が違う場合は差を記録し、その条件での一致を未確認とする。

| 比較資料 | 内容 |
| --- | --- |
| 比較元と製品 | 固定版の原画像、未加工screenshot、対象commit、撮影条件 |
| 差分 | 同座標50%overlay、無マスク・閾値0の全体diff、非一致画素数・割合、commandとtool版 |
| 診断領域 | 事前に認められた領域・理由。領域別診断でも全体diffを残す |
| 結果 | 実画像で確認した原因、修正・再撮影、残る差、未確認点 |

デザインマスターと実装は、同じ条件で寸法と全画素の全RGBAが完全一致することを完了条件とする。画面全体に加え、全部品の通常・hover・pressed・focus・selected・disabled等の実装に存在する表示状態を比較する。戦闘はHUDや操作ボタンなどのUI部品を対象とし、3Dや戦闘エフェクト、戦闘画面全体のフレーム・画面比較は作らない。文字やアイコンの描画差も除外せず、差分が残るケースと未検証のケースを未完了として扱う。比較単位は意味のあるUI部品全体とデザイン上のvariant・表示状態とし、関数の分割、内部の文字・図案、座標や任意の入力データだけを理由に比較対象を増やさない。素材は部品内で比較し、画像・アイコン単体のVRTは設けない。エディタ画面は原稿・VRTの対象外とする。

標準のFigma形式で再現できる意匠は、角丸や小数の行高等も含めて原稿で再現する。一般的なフレーム・コンポーネント・マスク・ブレンド等で構成し、比較時の描画経路を切り替えるための設定や、画素差を埋めるためだけの補助レイヤーを原稿へ入れない。誤差を消すことだけを理由に製品のスタイルを変更しない。保存形式の対応不足や出力処理の不具合は、再現不能な意匠と区別する。再現できない、または再現の実装が著しく複雑になる場合は、要素・寸法・文字・色・状態・挙動を保つ最小の実装整理を検証し、対象の全要素・全状態が比較で完全一致してから反映する。意匠や仕様を変える必要がある場合は、原因と具体案を示して本人へ確認する。

伸縮、位置合わせ、ぼかし、色補正、事後のmask拡張で不一致を隠さない。意図した変更、描画条件差、未承認の変更、実装不一致を区別し、実装不一致は同条件で修正・再比較する。

## 制作完了・採用・テストを区別する

| 確認 | 判断するもの |
| --- | --- |
| 視覚レビュー | 用途に対する見た目の品質 |
| 一致検証 | 固定版デザインの再現 |
| 操作テスト | 仕様上の入力と結果 |
| VRT | 既存baselineとの回帰 |
| ユーザーの採用判断 | 対象画面・状態・版の採用 |

独立レビューへは共通規則、対象仕様、原参考と固定成果を渡し、制作会話・過去の診断・期待する答えは継承させない。工程の実施は進行担当が実記録で確認する。未達を修正してから採用判断へ出し、意匠を変える場合はFigmaと対象仕様を更新する。

## 保存

保存先の指定を優先する。継続する仕様・手順はrepo、課題の判断・進捗・検証結果はIssue／PR、画像や保存して読む資料はSpaceで扱う。Spaceは正式なPage／reference経路を使い、読戻し・表示・受取側のアクセスを確認する。

原出力と必要な過去版を保持し、レビュー面には現行候補と判断に必要な比較を置く。公開範囲は[文書規約](../AGENTS.md#文書の更新)に従う。
