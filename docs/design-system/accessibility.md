# UIのアクセシビリティ

設計から制作・実装・検証へ通して使う共通要件である。採用済み・既存実装・未承認提案の区別は[基本デザイン](foundations.md)、部品固有の契約は[共通部品](components.md)、画面への適用は[画面設計とパターン](screens-and-patterns.md)、確認工程は[制作・検証手順](production-and-validation.md)へ辿る。文書の要件を製品全画面の達成済みとして扱わない。

## 共通して設計すること

| 対象 | 設計と確認の観点 |
| --- | --- |
| 意味と識別 | 必要情報を名前・操作名・状態・制約と対応付ける。装飾画像と意味のある図案を区別し、読み上げ名と可視ラベルを整合させる。色・形・位置だけに結果を依存させない |
| 入力とfocus | 必要な操作にキーボード・マウス・タッチから到達できること、入力順と視覚的な関係、focusの可視性・遮蔽・復帰、modalの背面抑止を設計する。hover限定の情報を作らない |
| 大きさと内容 | 容器とhit領域を分け、対象間隔と押しやすさを確認する。拡大・利用者の文字サイズ・狭幅・低い高さ・長文で必要情報と操作を失わない。比率縮小だけで対応済みとしない |
| 状態とエラー | 選択・focus・pressed・使用不可・待機を区別する。入力の理由・修正方法・保持される内容を伝える。失敗で入力や既存の保存を失わず、復帰と再操作条件を確認する |
| 視認性 | 必要な文字・図案・境界・状態の実隣接色と画像／透過下地を確認する。詳しい基準と尺度は[基本デザイン](foundations.md#読みやすさと入力) |
| 動きと進行 | 動きを減らしても対象・結果を示す。論理的なゲーム時間と演出時間を区別する。音・動きだけを唯一の情報源にせず、既存の入力・演出契約を保つ |

部品を再利用しても、画面の組合せ・コンテンツ・入力文脈・背景による新しい問題を確認する。部品固有の要件は部品の項目から参照し、画面設計票に今回の適用と未確認を記す。自動検査の成功を完成UI全体の適合としない。

## 検証と未確認の扱い

[テスト設計](../testing.md)に従い、意味入力・状態・focus復帰はmodel、実表示は直接撮影・画像比較、I/Oは実境界で確認する。支援技術や拡大・強制色等で未確認の条件は対象とともに報告する。画像上でfocusを描いただけ、読み上げ名を設定しただけでその入力や支援技術の動作を保証しない。現状の課題は対象Issueで追跡し、後付けで達成済みとしない。

[デジタル庁](https://design.digital.go.jp/dads/guidance/accessibility/)の工程全体で扱う構成、[SmartHR](https://smarthr.design/accessibility/standards-and-process/)の設計・実装・継続検証、[GOV.UK](https://design-system.service.gov.uk/accessibility/)の部品採用だけではサービス全体を保証しない考え方を参照する。本作の規則・入力・承認条件に対応付け、各社の組織体制や固有のfocus意匠を移植しない。
