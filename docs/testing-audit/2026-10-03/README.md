# 仕様とテストの対応監査（2026-10-03）

## 結論と読み方

現状は「テストが通る」ことと「実装済み仕様を漏れなく検証する」ことが一致していない。主な原因は、具体的な入力・結果に対応しないアサーション、CIから外れたテスト、画像を保存するだけの視覚確認、仕様文書の不整合である。有用な単体・結合テストを残し、各仕様が壊れたときに失敗する最小の検証へ整理する必要がある。

この記録の対象は **main [`4866de71c2200781926f2bdb9611410822163ca5`](https://github.com/karin0624/endfield_rpg/commit/4866de71c2200781926f2bdb9611410822163ca5)**。仕様・実装・テストソースを照合した静的監査であり、この監査でアプリ、テスト、CI、破壊テストを実行したとは報告しない。`assertion-present` は該当アサーションが存在するという意味であり、実行成功や機能全体の完全性を意味しない。反例は未実行の回帰候補である。

このディレクトリは監査時点の記録であり、新しいゲーム仕様や稼働済みのcoverage gateではない。現在の仕様の正本は `specs/`。PR #100 の改善は main の保証に加算せず、[監査時点の差分](pending-pr100.md)に分ける。

## 先に直すべき穴

1. **CIの実行範囲。** [現在のブラウザ実行コマンド](https://github.com/karin0624/endfield_rpg/blob/4866de71c2200781926f2bdb9611410822163ca5/package.json#L13-L21)は `built/debug/ui` のみ。[settings project](https://github.com/karin0624/endfield_rpg/blob/4866de71c2200781926f2bdb9611410822163ca5/playwright.config.ts#L38-L40)にある設定API、renderer寿命、地形cullingは通常CIで実行されない。テストの不存在とCIの除外を分けて修正する。
2. **テスト名より狭いアサーション。** 候補カードの連続実入力、購入時の二重確定、物品使用後の敵行動、控えへのXP非付与などは、名前に書かれていてもその条件を作って結果を確認していない場合がある。各入力直後の状態や、回帰すると変わる独立期待を使う。
3. **古い観測値での不変確認。** [party fixture](https://github.com/karin0624/endfield_rpg/blob/4866de71c2200781926f2bdb9611410822163ca5/tests/fixtures/party-selection.html)の `#state` は初期化・確定・明示snapshot時だけ更新される。編集中にsnapshotを更新せず同じ文字列を比較しても、本番状態が変わらなかった証明にはならない。既存の順序・focus・scrollの有効な検証まで削らない。
4. **見た目の代用。** スクリーンショット保存、動画、手動overlay、CSS色・class・変数の一致は、自動画像合否判定ではない。[画像比較スクリプト](https://github.com/karin0624/endfield_rpg/blob/4866de71c2200781926f2bdb9611410822163ca5/scripts/compare-party-ui.py#L75-L91)は差分を出すが、画素差自体では失敗しない。必要な画面状態の承認済みruntime基準とVRTへつなげる。
5. **不正入力・失敗・境界。** 会話/ダンジョン定義の拒否、保存された習得状態の破損、装備の現行API、設定parserの各範囲、設定保存の並行/サイズ/失敗時保持、非root配布、entryのpagehide/BFCacheなどを、安価で直接的な層に割り当てる。
6. **仕様衝突。** 保存のv4記述とv5-only、旧編成の取消説明、debug URL、商店/装備対象外の古い説明が残る。現行仕様を勝手に縮めて不足を消さず、正本の不整合を解消する。重要物品による分岐は、所持サポートと本番分岐実装を混同しない。

## 採用する最小のテスト構成

既存の TypeScript/Biome、Vitest、Playwright を使う。比率やテスト件数を目標にせず、どの層で失敗を直接検知できるかで決める。

| 層 | 担当する契約 | 例 |
| --- | --- | --- |
| 静的検査・build | 型、整形、素材同梱、test discovery、契約参照の整合 | 新testがrunner対象外になったら失敗 |
| 単体 | 公開純粋関数の計算と境界 | 選択枠の追加/解除、命中境界、設定parser拒否 |
| ドメイン結合 | 本番core間の状態遷移 | 使用→敵行動→帰還→保存、再送拒否、療養と控え |
| UI結合 | 本番mountとcoreの入力・表示接続 | native連続click、keyboard、focus復帰、待機中の操作抑止 |
| renderer/API結合 | 実WebGL・HTTP・一時ファイルの公開契約 | 資源解放、遅着の隔離、保存失敗時に元データ保持 |
| 通常配布E2E | 実entry・配布物・代表的な一連操作 | 開始→編成→探索→戦闘→帰還→保存/再開 |

VRTは視覚契約を検知するための判定方法であり、入力・core・保存の代わりにはならない。反対にARIA/focus/disabled/公開状態のアサーションは、画像と役割が違うため維持する。WebGL資源数、描画回数、HTTP取得回数も、再利用・解放・静止描画回避が仕様なら意味のある観測である。

## 次の実装と以後の開発フロー

1. 本監査の行を統合し、実装済みの意味契約を現行specに照合する。同じ契約の重複、試用値、未実装計画、仕様衝突を整理し、必要な境界を分解する。
2. 一つの小さな維持用catalogを用意する。安定ID、spec参照、対象実装、前提/入力、期待結果、検証層、test参照、具体的なアサーション、状態を持たせる。監査JSONを無検討にそのまま実行gateへ流用しない。
3. test側にもIDを結び、validatorはID一意・参照存在・runnerによる発見・実行結果を照合する。実装済みなのに不足/未監査/仕様衝突が残ればgateを失敗させる。構文一致だけでアサーションの意味や仕様網羅を証明したとは扱わない。
4. 初回は全領域の既存不足を解消する。その後の各PRは追加/変更/削除した契約ID、影響する層、影響なしの理由、必要な負例を示す。新specやtestがどの領域にも属さない状態を検出する。
5. 通常CIは静的検査、Vitest、normal/debug build、全ブラウザproject、catalog/discovery/result検査を実行する。`.only`を拒否し、意図したskipは理由と代替実行を限定管理する。差分選択は実測で必要になるまで追加しない。
6. 修正した既知バグは、原因を戻すなど適切な負例で対象アサーションが失敗することを確認する。全テストへの巨大mutation基盤や、数個の負例による全仕様完全証明は不要。
7. baseline更新には対象契約・理由・画像差分のレビューを付ける。CIで自動更新したり、許容差を広げて不具合を隠さない。runtime VRT一致と、完成デザインへの承認は別の証拠として扱う。
8. 最終head SHAの全gateと差分を確認する。アーキテクチャPRを作成後、merge前に、具体ケース→検知するtest→使用技術→残る限界を説明する。

2026-10-03のGitHub読み取りではmainの保護は無効と表示され、required checksによる強制は確認できなかった。詳細の一部はプラン/権限制約で取得できない。手続きでheadと結果を確認することはできるが、GitHubの保護設定による強制と同一ではない。本記録は設定変更を行っていない。

## 無駄なテストを増やさない

- テスト内で作ったコピーや、本番関数へ渡していない値の不変確認を、本番の副作用検証として数えない。
- 期待値を検証対象と同じ本番計算で作らない。一方、仕様にある独立したHP/RNG/個数などの数値期待は残す。
- 廃止されたAPIのテストを現行経路の保証に数えない。現行APIの必要な拒否・所有・状態遷移を揃えてから旧caseを削除する。
- 全core境界を全viewportのE2Eへ複製しない。代表的な通常経路と、固有の入力/配置境界を選ぶ。
- 削除ごとに、旧caseの契約と残る代替保証を対応付ける。「内部値」「unit」「重複」という分類だけで削除しない。

有限のテストで未知の全入力を保証するとは約束しない。実装済み仕様の各約束について、どの入力と独立した判定が破綻を検知するかを明示し、変更のたびに維持することを完成条件とする。
