# デザインシステム

プレイヤーが状況と操作の結果を理解できるUIの共通規則。ゲーム規則は[仕様概要](../specs/overview.md)、具体的な割当は[画面設計](ui-screen-design.md)、実画像の確認は[制作手順](ui-asset-production.md)を参照する。

## 設計原則

### 判断に必要な情報から始める

画面の情報は0個から考え、理解・判断・操作に必要な要素だけを置く。各語句にも残す理由を求める。常設する必要がなければ、必要な場面で示す。入口をメニューへ移す際も、その行為がいつ必要になるかを検討する。

構造や図案で意味を伝え、名前・数値・操作名・制約・結果に必要な文字を加える。管理番号や制作状況、同じ意味の言い直しは表示しない。支援技術向けの名前・説明と、判断に必要な視覚階層も保つ。

### UIの言葉

操作ラベルは行為と結果、状態表示は現在の状況、エラーは起きたことと次にできる操作を示す。同じ意味には同じ用語を使う。内部ID・開発用の画面名・曖昧な修飾語は表示せず、数値と単位、未確定と確定、選択と実行、保存と移動を区別する。

対象と結果が分かる日本語を使う。見出し・ラベル・補足で同じ内容を繰り返さず、具体文言は画面仕様と投影データで管理する。

### 機能と外観を対応させる

名称だけでなく、入力後の結果、確定の有無、取消、対象、危険性を比べる。機能が近い操作は外観と大きさも近づける。外観が完全に同じなら機能も完全に同じであることを確かめる。異なる対象・行為は、図案・ラベル・形・配置・状態のうち意味に必要な差で識別できるようにする。

同じfamilyの一貫性を保ち、役割・判断・優先度に応じて大きさ・色・強調を変える。使用頻度や重要度を実測していなければ仮説として扱う。画面が違うだけで意匠を変えない。

### 画面全体で階層を作る

今判断すべき内容へ注意が向くよう、面積、位置、文字、色、余白を組み合わせる。関連情報はまとまりとして見え、異なる群との境界は分かるようにする。各要素を単独で強調し続けない。背景や人物の占有面積も、画面の目的と必要な判断に対して選ぶ。

一つの画面で成立した配置、装飾、承認済みの寸法を別画面の規則へ拡張しない。承認済み画面を実装するときは、その固定版の範囲を保つ。

## 基盤と意味トークン

基盤は値の体系、意味トークンは用途、部品契約は組合せと振る舞いを表す。背景・書体・縮尺が変われば見え方を再確認する。サイズ段階やvariantは、必要な用途がある場合に追加する。

共通の役割は同じトークンを使い、部品固有値はその部品へ閉じる。実装と値の所在は[画面一覧](ui-screen-design.md#現行画面への入口)を参照する。

| 意味 | 現在の通常UIトークン | 使用条件 |
| --- | --- | --- |
| 操作面 | `--ui-surface`、`--ui-hover`、`--ui-pressed` | 通常・ポインター反応・押下中 |
| 文字 | `--ui-ink`、`--ui-muted` | 主情報と補助情報。必要な理由を読めなくしない |
| 境界 | `--ui-metal` | 情報群や操作の外形 |
| 選択 | `--ui-selection`、`--ui-selected-surface` | 選ばれた内容。focusとは別 |
| 主操作 | `--ui-primary`、`--ui-primary-hover`、`--ui-primary-pressed`、`--ui-on-primary` | 目的を進める強調と、その上の文字 |
| キー入力先 | `--ui-focus` | 通常・選択・押下と併存するfocus表示 |
| ゲーム情報 | `--ui-hp`、`--ui-danger` | HPと危険。操作強調と混同しない |

値が同じでも、選択・危険・属性等の異なる意味を一つに統合しない。上表は既存通常UIの対応であり、全画面への適用宣言ではない。絵付き拠点UIの色・素材・寸法は[拠点部品仕様](ui-screens/hub-components.md)に限定する。同じ役割でも、通常UIの色を画像へ上塗りして意匠を変更しない。

### 文字

本文、操作ラベル、主要数値、見出し、補助情報を区別し、書体・太さ・サイズ・行高・字間を一組で定義する。戦闘中に読むHPや対象名、行為を選ぶラベル、落ち着いて読む説明では、読む速さと密度の条件が異なる。背景と実書体を含む画面で必要な情報が読め、優先順位が分かるようにする。

既存通常UIの対応は次のとおり。値の正本は[ui.css](../src/web/ui.css)。換算値はroot 16px時。

| 用途 | トークン／値 | 表現 |
| --- | --- | --- |
| 本文・説明・状態・理由 | `--ui-body-size` / 1rem（16px） | Noto Sans JP 400、本文行高1.6 |
| 操作・主要数値 | `--ui-action-size`、`--ui-emphasis-size` / 1.25rem（20px） | 操作はNoto Serif JP 500、行高1.4 |
| 人物見出し | `--ui-name-size` / 1.5rem（24px） | 対象部品の太さを確認 |
| 補助情報 | `--ui-caption-size` / 0.875rem（14px） | 本文や操作不可理由の代用にしない |
| 画面見出し | `--ui-title-size` / 3rem（48px）、幅900px以下で2rem（32px） | Noto Serif JP 500、行高1.4、字間0.04em |

新しいfamilyは役割と階層、実書体、表示縮尺、最長文言から文字スタイルを決める。拠点UIのラベル等は[専用仕様](ui-screens/hub-components.md)に従う。文字を収めるための縮小・横潰しを避け、改行、領域、配置を見直す。利用者のroot文字サイズを固定pxで上書きしない。数値の比較には等幅数字を使い、最大桁、長名、症状名、操作不可理由で読めることを確かめる。

### 寸法・余白・整列

部品内、同じ群の部品間、群同士、画面端の余白を役割で分ける。同じ判断に使う情報がまとまりとして見え、別の操作や背景の対象から分離して読める距離を選ぶ。密度を下げるための空白と、関係を伝える空白を区別し、画面全体で釣合いを確認する。

余白は文字や図案の可視端を基準に見る。透明領域、focus枠、入れ子のpaddingやborderも含め、不規則な枠では最狭部と偏りを全周で確認する。

余白は情報の関連・密度・強調から決め、書体や図案の重心に合わせて光学調整する。状態切替で部品を跳ねさせない。中央揃えは内容を入れる有効領域を基準にし、可変の内容長でも保つ。入り切らなければ一律縮小より先に配置を見直す。

### 面・形・境界

面は関連情報のまとまりや背景上の読取り、枠は部品の外形や状態の識別を支える。角の形、線、塗り、影は、意味と階層が変わらないのに画面ごとに変えない。画像由来のframeと通常UIの縁は、異なる構成として扱う。

通常UIの角落ちは`--ui-cut-size`、部品の境界は`--ui-metal`等の役割と実装を参照する。focus外周を装飾のclipに巻き込まない。背景と内容の間に面を設ける場合も、面の存在だけで読めると判断せず、合成後の隣接関係で確かめる。

### アイコンとイラスト

操作を示す通常アイコン、対象を識別する図案、人物portrait、装飾を区別する。アイコンが含まれるだけで、通常のIconButtonと絵付き入口を同じfamilyにしない。

図案box、可視の占有面積、外枠、ラベル込み部品、操作領域を別々に定義する。透明余白や原画像の解像度は表示推奨サイズではない。共通サイズは入力方式、実表示、ラベル、識別性から選び、光学的な釣合いを実画像で比較する。alpha面積の一致だけで均一と判定しない。

図案の形とラベルの双方から対象が分かり、隣接する入口と見分けられる大きさを選ぶ。単純な記号と複雑なイラストは、細部の識別に必要な大きさと部品全体の占有面積を比べる。原図案を使う対象では輪郭・形状・顔や特徴を保ち、許可された表示範囲や加工を画面仕様で定める。原本を保存しつつ配置用cropを使い、不要な透明域を守るために図案を過小化しない。

### 色・コントラスト・動き

選択、focus、操作不可、危険を色だけに依存させない。必要な文字、輪郭、内部線、状態表示について、実際の隣接色と合成後の下地で確認する。画像・半透明の上では場所と状態によって下地が変わる。情報を絞った後で注目先にアクセントを使い、色・大きさ・明暗・配置が同じ優先順位を示すようにする。重要な受動情報を文字だけへ落とさず、背景の明度・彩度・細かな明暗差との競合も確認する。背景を暗くすること自体を目的にしない。

通常文字は4.5:1、大きな文字は適用条件を満たす場合3:1、識別に必要な非テキストは3:1を設計基準とする。装飾や非活性部品へ同じ閾値を機械適用しない。文字の大きさ・太さ、状態、情報として識別が必要かを区別して適用する。数値や自動検査だけでWCAG全体への適合を宣言しない。

動きは対象・結果の理解を補助する。動かない状態でも意味を識別できるようにし、動きを減らす設定に対応する。演出時刻からゲームの確定処理を再実行しない。戦闘・会話のマーカーの使用条件は[戦闘画面](../specs/visuals.md)と[会話](../specs/adventure.md)に置く。

### 入力とアクセシビリティ

マウス・タッチ・キーボードで同じ意味の操作へ到達できるようにする。可視図案と操作領域を分け、focusの外周、ラベル、状態・理由の読取りを保つ。読む順とTab順を構造に対応付け、通常画面に不要なfocus閉込めを作らない。dialogでは初期focus、背面抑止、Tab範囲、終了後の復元を定める。

操作の発見、入力先、結果の通知を確認する。アクセシビリティへの適合を主張する場合は対象・基準・実際の検証を示す。

## 部品の契約

familyは役割と振る舞い、variantは用途別の使い分け、stateは現在の状態を表す。variantの追加には既存契約で不足する条件を示す。構成・密度・余白を決め、実際の絵と文字で確認する。名称よりも対象の役割と構造を優先する。

| family | 役割・構造 | variantを選ぶ条件 | 状態・入力契約 |
| --- | --- | --- | --- |
| Button | 一つの行為を起こすラベル付き操作。必要なら補助アイコン | 通常／主操作／戻るを行為と優先度で選ぶ | 通常・hover・pressed・focus・disabled。クリック／タップ、Enter／Spaceの一入力を一行為へ |
| IconButton | 通常の短い操作を一つの記号で示す | 記号だけで識別できる用途。曖昧なら可視ラベル付きButton | Buttonと同じ。可視ラベルが無くてもaccessible nameを持つ |
| IllustratedAction | 対象図案・横長frame・ラベルを一体にした入口 | 管理と移動等の役割差を、採用された図案・frame・ラベルで識別 | 入口の意味と結果を保持。画像を押下領域の代用にしない |
| PlaceEntry | 背景内の場所・人物と対応する図案・frame・ラベル | 施設／人物／行き先。空間との対応が必要な入口 | 背景anchorと読む順を別に設計。focusは全体を示し、図案とラベルを別操作にしない |
| PassiveStatus | 時刻・資源・状態等、判断に必要な受動情報 | 情報種別で選び、操作可能な外観との混同を避ける | Tab対象にしない。値・単位・状態を読み上げでも識別可能に |
| ChoiceCard | 比較と選択に必要な情報をまとめる | 選択方式、詳細への入口、必要な比較情報による | 未選択・選択・focus・不可を区別。詳細を見る操作と選択を区別 |
| Field | 値を入力し、制約と不正理由を関連付ける | 数量等の入力型と確定点による | ラベル、範囲、不正値、未確定draft、focus。入力だけで確定しない契約は維持 |
| Dialog | 背面操作を止め、一つの判断に集中させる | 選択、確認、処理待機を区別 | 読む順、初期focus、Tab範囲、取消、終了後の復元、失敗時の保持を定義 |
| Feedback | 操作の結果・失敗を必要な時点で知らせる | 受動通知と、読取り・scrollが必要な領域を区別 | 読める期間と到達性を確保。通知のために現在の入力先を奪わない |

操作の強調は、その場面で進める判断と結果に対応させる。主操作と補助操作の差、同格の選択肢の関係、実行できない理由が、周囲を含む配置と状態から分かるようにする。図案が主体の入口でもラベルと入力先を保ち、受動情報を押せる部品に見せない。

部品には用途・構成・内容制約・状態・入力・focus・伸縮・欠損時の扱いを定める。長い日本語、文字拡大、可変幅でもラベルが読め、隣接操作と混同しないことを確認する。実装は[画面一覧](ui-screen-design.md#現行画面への入口)、拠点の値は[部品仕様](ui-screens/hub-components.md)、選択・詳細は[編成仕様](../specs/party.md)を参照する。

### 状態の組合せ

hoverはポインター位置、pressedは押下中、selectedは選択内容、focusはキー入力先、disabledは現在許可されない操作を表す。互いを代用しない。focusとselected等は同時に成立する。状態を見せるためだけに新しい選択段階や確認を追加しない。

待機中は処理対象と再入力の可否、失敗時は保持される内容と再操作の入口を示す。実際のゲーム制約と開発途中の未接続を区別する。表示案の未接続を理由に意匠をdisabledへ変更せず、動作完成とも報告しない。

## 複合パターン

複数の部品を組み合わせる際は、判断の順序、状態の保持、入力先と復帰先までを一つの関係として設計する。同じ判断の流れを画面ごとに作り直さず、必要なパターンを共有する。

| pattern | 組み立てる関係 |
| --- | --- |
| 入口群 | 目的が近い入口をまとめ、同格の見た目を揃える。図案とラベルで対象を区別し、読む順・操作順を意味に合わせる |
| 背景上の場所選択 | 場所と入口の対応、重要な背景の遮蔽、隣接部品との関係を同時に扱う。狭幅では到達可能な通常flowへ切り替える |
| 選択と詳細 | 選択状態を保持して詳細へ進み、戻った際に元の対象・scroll・focusへ復帰する。見ることと確定を混同しない |
| 入力と確定 | 入力draft、検証、確定、取消を分ける。無効値でも修正でき、取消による保持・破棄の範囲が予測できるようにする |
| 確認と保存 | 対象と影響を先に読み、実行／取消を選ぶ。I/O成功、ゲーム状態の確定、画面遷移を別の出来事として扱う |
| 結果と復帰 | 結果を必要時に提示し、通常操作へ復帰する。長い通知は読める領域として到達可能にする |

layout・状態・値は画面仕様で決める。固定位置や画像寸法をpattern自体の普遍値にしない。狭幅・低い画面・長文・文字拡大・最大桁と関連状態で、まとまりと操作可能性を確認する。

## 画面への適用と更新

全要素の割当と差の理由は[画面仕様](ui-screen-design.md#画面ごとに決めること)へ記す。

規則は実画面の読みにくさ、識別、余白や階層の問題から見直す。改善の仮説を部品・状態・全体画像と影響する別画面で比較し、利点と弊害を確認する。複数の用途に成立する条件は共通規則へ、一画面の条件は画面仕様へ置く。

意匠に影響する変更はユーザーのデザイン判断へ戻す。

視覚レビューと固定版の一致確認は[制作手順](ui-asset-production.md)に従う。
